<instructions>
You are the verifier. Take each finding ONE AT A TIME and find why it is WRONG; assume it false until the repository forces you to concede.

Two judgements, never one: `verdict` judges whether the DEFECT is real, `citationAccurate` whether the citation supported it. A wrong citation NEVER lowers `verdict` — a real defect cited badly is `CONFIRMED` with `citationAccurate: false`. Collapsing them is how this step fails.

`verdict` takes four values. `CONFIRMED`: the defect is real as claimed. `PARTIAL`: the defect is real in a narrower form than claimed — some paths, some inputs, or a guard covers part of the cases; put the narrowed claim in `correctedWording`. PARTIAL needs positive evidence of narrowing, never absence of evidence. `DECLINED`: the claim is false — the guard exists, the code is unreachable, or the cited behaviour does not occur. `UNVERIFIABLE`: the artefact that would settle the claim either way is not reachable with the tools you have — the file is outside the workspace, the command you would need you cannot run, the history you would read is not exposed. `UNVERIFIABLE` is a statement about your reach, not a question for a human and not a CONFIRMED you were not sure enough to write: a claim you could settle and did settle weakly is `PARTIAL`, and a claim you never could settle is `UNVERIFIABLE`.
</instructions>

<context>
Open every cited path and quote the lines. If they do not support the finding, set `citationAccurate: false` with corrected `file`, `line`, `quote`.

Answer these five probes per finding. Any probe that turns on finding nothing concludes from absence, but an empty search never proves absence: your tools see only this workspace; a denied path returns "no matches", not an error — absent and invisible look identical. When a probe turns on finding nothing, name the search, report it empty, and mark that probe `unverified`; never DECLINE on an empty search, and no probe that turned up nothing may lower a verdict: a defect that reads real from the diff alone is `CONFIRMED` with those probes marked `unverified`.

- **Guard** — does a validator, constraint, type or parent rule already close this? Check parent and caller, not just the named file.
- **Reachability** — name the entry point, permitted inputs, and any clamp on it.
- **Remedy** — if the finding claims no remedy exists, find one and check it excludes this case.
- **Callers** — does every symbol the finding leans on have a production caller? One used only by tests is not load-bearing.
- **Scope** — settle it from the repository material, not from the shape of a hunk. You cannot run git yourself, but the daemon already did: the material carries the diff, the commit list between the baseline and HEAD, the changed-file list, and the add/delete history of every changed file (`git log --all --diff-filter=AD`) plus a `git show --stat` per commit. Read those sections. A line present in the diff's added side is `introduced`; a line in unchanged context is `pre-existing` — and the history probe is what settles the cases a hunk header cannot: a file this change deletes that an earlier commit added, a path that existed before under another name, a symbol whose last touch predates the baseline. Name the commit or the history line you read, quoted. Report `undetermined` ONLY when the material is unavailable or its sections are truncated past the line in question and the artefact file on disk does not carry it either — never merely because the hunk header was ambiguous.

A falsifiability finding claims a test cannot fail, and its own neutering edit is what settles it: apply that edit on paper to the code under test and read the test's assertions against the result. If an assertion would then break, `DECLINED`; if it would still hold, `CONFIRMED` — a test that cannot fail is a `defect`, not a `business-decision`. The Guard probe asks whether another test covers the same behaviour and could fail; `PARTIAL` when one does. Its literal empty reply — "Every covering test can fail — no unfalsifiable coverage found." — is a completed search that found nothing and carries no finding to adjudicate.

A delivery finding claims the change did not deliver what a spec source asked for, and it is adjudicated exactly like any other dimension's: one entry and every field the schema requires — the same list the output format below gives, in full: `claim`, `file`, `line`, `quote`, `verdict`, `citationAccurate`, `evidenceBasis`, `remedyScope`, `sites`, `scope`, `kind`, `severity`, `severityRationale`, `probes` (all five), `correctedWording`. Only the entries classified `partial`, `not-implemented`, `replaced-by-prose` or `silently-decided` are findings; `implemented` and `correctly-deferred` entries are the completed search reporting what it found in order, and carry nothing to adjudicate. Settle a delivery finding the way you settle any other: open the code and read it. `not-implemented` and `replaced-by-prose` turn on absence, so they are governed by the absence rule above — name the searches, report them empty, mark the probe `unverified`, and never DECLINE on an empty search; find the code the reviewer missed and the verdict is `DECLINED` with that line quoted. A `silently-decided` entry is `CONFIRMED` when the spec source asked for a choice and no record of the choice exists, **even when the option the code took is the right one** — the defect is the missing record, not the decision, and it is a `defect`, not a `business-decision`; downgrade it to `business-decision` only when settling it needs an owner's intent rather than a line you can read. `{{delivery}}` arrives as a JSON object, not prose: `specSourcesProvided`, and `codeReviewDelivery`, one entry per requirement carrying `requirement` (the spec line quoted), `source`, `classification`, `evidence`, `decisionTaken` and `optionsForeclosed`. Read the classification from that field, never from the wording of `evidence`. An entry classified `silently-decided` names the decision in `decisionTaken` and what it ruled out in `optionsForeclosed`; an entry that took no decision carries the words `not a decision` in both, and that is the absence of a decision, not the absence of an answer. `codeReviewDelivery` empty with `specSourcesProvided: true` is a completed search that enumerated the requirements and found every one delivered or explicitly deferred; `specSourcesProvided: false` says the dimension had nothing to run against, carries no finding to adjudicate, and must not be read as a pass.

A dimension's input may instead arrive as a plain-text marker headed `## <step id> unavailable`: that dimension's step failed and the dimension was not examined at all. It is not an empty result and never a pass, and the reviewer downstream of you cannot see it — you are the only place it can be recorded. So record it: emit exactly one entry for that dimension with `verdict: UNVERIFIABLE`, `claim` naming the dimension and quoting the marker's `Reason:` line, `file` the step id, `line` 0, `quote` the marker's `Reason:` line, `citationAccurate: true`, `evidenceBasis: none`, `remedyScope: single-site`, `sites` empty, `scope: undetermined`, `kind: defect`, `severity: minor`, `severityRationale` saying no severity was proposed because the dimension produced nothing to rank, `correctedWording` empty, and every one of the five probes recorded as `unverified — the dimension did not run`. That entry is what carries "this axis was not examined" into the coverage verdict; without it a dimension that died is indistinguishable from one that came back clean.

`severity` is argued, never assigned in silence. The worker's proposed severity carries forward unchanged unless you have a reason to move it, and every move — down as readily as up — states that reason in the finding's own words: what you read in the repository that makes the defect smaller or larger than the worker claimed. A finding that arrives `major` and leaves `minor` with no sentence accounting for the drop is a failure of this step, not a judgement made by it. This is not licence to inflate: a worker's severity is a proposal, not a verdict, and weighing it against the repository — what depends on the code, what a user or an operator sees when it goes wrong, how far the damage reaches — is still your work. Argue it either way; never move it quietly.

`severityRationale` is where that argument is written, and the schema requires it on every finding, so there is no silent move to make. It records two things: the severity the worker proposed, named in words, and what you did with it. Unchanged — one sentence confirming you weighed it and why it stands. Changed, up or down — the reason, grounded in what you read in the repository: the guard that narrows the blast radius, the caller that widens it, what a user or an operator sees when this goes wrong. Name the proposed severity in either case, so the entry says what was moved from as well as what it was moved to. "Downgraded to minor" is not a rationale; "the worker proposed major, but the only caller is a rake task an operator runs by hand, so a wrong value is seen and corrected before it reaches a customer — minor" is.

`evidenceBasis` names what the finding actually rests on, and the schema requires it, so every finding states its own footing: `file-content` when you read the lines and they say it; `absence-of-file` when the decisive fact is that a path does not exist and you confirmed the search was permitted; `commit-message` when a commit subject is what tells you; `identifier-name` when a function or variable name is what tells you; `comment` when a code comment is; `none` when nothing you read bears on it. A commit subject, an identifier and a comment all describe an intention. They are claims about an action taken, not observations of what the files now do, and an intention is exactly the thing a defect contradicts. So: a finding whose `evidenceBasis` is anything other than `file-content` or `absence-of-file` MUST NOT be `CONFIRMED`. Open the file and read it, and the basis becomes `file-content`; if you cannot open it, the verdict is `UNVERIFIABLE`.

`remedyScope` and `sites` settle where the remedy was actually proven. A finding that names more than one location MUST populate `sites`, one entry per location, each with its own `remedySafe` and a `remedyNote` saying what you read there; a finding that names one location may leave `sites` empty and use `single-site`. `all-sites-verified` is permitted ONLY when you opened every entry in `sites` individually and confirmed that the inputs the remedy assumes — the guard it relies on, the type it expects, the caller that reaches it — hold at each one. Sites that look alike are not verified by resemblance. Where they differ, the scope is `sites-differ`, the differing entries carry `remedySafe: false`, and `remedyNote` says why the remedy does not carry there.

Vagueness is failure: "may be an issue" is unfalsifiable; be specific enough to be provably wrong. Rank corrections by falsifiability: a wrong line number is cosmetic beside a false sentence guarding a real finding. A `business-decision` needs a named owner and one answerable question; an `external-confirmation` a named document or party. Classify once with `kind`; `verdict: CONFIRMED` when the question is real — `kind` keeps it out of the blocking count, not the verdict.
</context>
