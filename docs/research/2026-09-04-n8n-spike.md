# Spike: can n8n be yoke's engine + editor? (2026-09-04)

Throwaway spike to answer, before deciding build-vs-adopt: **can n8n's visual editor and
execution engine drive a coding-agent CLI (`claude`) inside a real repo, read-only, chaining
output between steps, with per-step model choice?**

## Setup

- `npx n8n@1` (v1.123.77) on the host. **n8n 2.x needs Node ≥24** (we run 22) and **disables the
  Execute Command node by default** with a known re-enable bug ([#23439](https://github.com/n8n-io/n8n/issues/23439));
  pinning to 1.x sidesteps both. Node ran on the host so `claude` (2.1.259) and its auth were
  already present — no container CLI/auth problem.
- Throwaway target repo with `math.js` (`add(a,b)`) + `README.md`.
- Headless: built a workflow JSON (Manual Trigger → Execute Command → Execute Command), imported
  via `n8n import:workflow`, ran via `n8n execute`. Did **not** create the owner account / use the
  logged-in editor (account-creation is not something this session does automatically), so the
  engine/capability was proven headlessly; the editor UX was not clicked through.

## Result — it works

Workflow `status: success`. The Execute Command node ran
`cd <repo> && claude -p '…' --allowedTools 'Read,Glob' --model sonnet` and claude returned, verbatim:

> Source files: `math.js` (only source file; `README.md` is docs).
> `add()` in `math.js:1` returns the sum of its two arguments, `a + b`.

Real read-only codebase grounding, driven by n8n. The second node received `135 chars from previous
claude output` — data chains between steps (once the value is in n8n expression mode, `=…{{ $json.stdout.length }}`).

Per-step model switching = the `--model` flag on each node. Free for private self-host (Sustainable
Use License permits internal/personal use).

## What it costs / what you rebuild

- **The coding agent is a shell string, not a typed step.** You hand-write
  `cd repo && claude -p '…' --allowedTools 'Read,Glob' --model …` in a text box. n8n has no notion of
  a `role`, a declared `workspace: read|write` sandbox, a model registry, or provider fallback — the
  exact abstractions yoke has (we just built `workspace: "read"` → `--allowedTools "Read,Glob"` as a
  typed, validated step). In n8n these become hand-maintained shell strings.
- **Definitions live in n8n's DB, not git-backed YAML** (against ADR-0003). Reviewing a pipeline
  change in a PR becomes an export/import dance.
- **Operational friction:** Node-24 requirement for 2.x, Execute-Command disabled-by-default + the
  re-enable bug, an owner-account gate, and n8n's own expression syntax.
- **HITL/gate** exists (Wait/approval nodes) but is n8n's model, not yoke's suspend/resume.

## Verdict

n8n genuinely **can** be the engine + editor: it drives `claude` in a repo, chains steps, switches
models per node, free for private self-host, with a mature canvas. It gets ~80% of the way with zero
build.

What it does **not** give — and what yoke's design is specifically about — is the coding agent as a
**first-class, typed, git-backed** step: declared read/write repo sandboxing, a role→provider
registry with fallback, and neutral YAML definitions reviewable in git. In n8n those are shell
strings in a database.

**Recommendation (decision still the owner's):** the spike lowers the risk of adopting n8n but does
not erase yoke's reason to exist. Two honest options:

1. **Adopt n8n** as the engine+editor and accept coding-agent steps as maintained shell strings —
   fastest to a working tool, weakest on typed/git-backed structure.
2. **Keep building yoke** (React Flow editor) for the typed, git-backed, sandboxed coding-agent
   model — more work, but it is the thing no off-the-shelf tool provides (see
   `2026-09-04-n8n-and-alternatives.md`).

A viable hybrid also exists: yoke stays the source of truth and typed runtime, and n8n is offered as
an optional execution/edit surface for those who want its canvas — but that is a later question, not
this decision.

Spike instance and target repo were throwaway (scratchpad); n8n was stopped after.
