## Problem

A new user runs `pnpm doctor` and sees nothing, because a built-in pnpm command shadows the package script. A developer installs workflows into a project's `.agent-flows/pipelines/` directory and runs a daemon that ignores them, instead serving the tool's bundled pipelines from its own checkout. An MCP client lists a pipeline the HTTP daemon cannot execute, and can run a stale version after the user edits it. The chat system and the CLI each have their own rule for how to specify the project under development. The HTTP API returns `running`, `suspended`, `success`, and `failed` statuses, while the MCP documentation promises `awaiting_approval`; when a gate is rejected, the caller sees a error payload, not a normal outcome. The web page renders an "Edit in n8n" button even when n8n is not configured. The pnpm script surface speaks three different command conventions: bare names (`doctor`, `serve`, `mcp`), domain prefixes (`canon:check`, `bindings:claude`), and verb suffixes (`flows:install`, `evals:run`). None of these are usability bugs in isolation; together they form a surface that contradicts the principle of least surprise at every entry point. The tool is deterministic and single-owned; fixing this requires renames and breaking changes to the HTTP API contract, which is acceptable because the tool is private and has never been in production use.

**Findings:** All of the following were reproduced live today (2026-09-08) against a real sandbox project and exist in the current codebase:

- F1: `pnpm doctor` prints nothing and exits 0 (`package.json` line 96 has `"doctor": "…"`, shadowed by pnpm's own `doctor` command; only `pnpm run doctor` reaches the real preflight).
- F2: Installing workflows into a project has no effect on a running daemon. A daemon started with 0 project workflows still returns the 11 bundled ones on `GET /api/pipelines`; after restart, returns the project's installed set. The daemon log states `pipelines from bundled (…)` vs. `pipelines from project (…)` (`src/serve/server.ts:1279-1281`).
- F3: The MCP tool `list_pipelines` re-reads from disk on every call (code comment at `src/bindings/mastra/server.ts`, line 74), while execution goes through the daemon, which resolves once at startup. The chat can list a pipeline the daemon cannot run, and can run a stale version after a user edits one.
- F4: Two different targeting rules: `flows:install` and `serve` require `AGENT_FLOWS_PROJECT_DIR` environment variable; the MCP server takes the directory it was launched from (captured in `scripts/mcp-serve.sh` before directory change). Both are documented and both work.
- F5: Status vocabulary differs by surface. `GET /api/runs/:id` returns `running`, `suspended`, `failed`, `success`. The MCP `run_pipeline` tool description (source: `src/bindings/mastra/server.ts:99`) promises `awaiting_approval`. A caller never matches the documented name.
- F6: Rejecting a gate returns to the chat as an error payload: `{"error":"GateRejectedError: Gate \"plan.approve\" rejected (manual): no reason given"}`. Rejection is a normal, intended outcome, not a tool failure. The run's terminal status becomes `failed`, not distinguishing "a human said no" from "something broke" (`src/runtime/runService.ts:100-109`).
- F7: The web page renders an "Edit in n8n" button beside every workflow even when n8n is not configured. The page header states `n8n: not configured` simultaneously (`src/serve/ui.html`, line 710 shows the button; configuration status is checked at line 390).
- F8: There is no `agent-flows` executable — `package.json` has no `bin` entry — yet the MCP server's error text tells users to "start it with \"agent-flows serve\"" (`src/bindings/mastra/server.ts:31`).
- F9: The pnpm script surface is inconsistent: `canon:check`, `bindings:claude`, `bindings:n8n`, `flows:install`, `flows:list`, `mastra:smoke`, `evals:run` sit beside bare `doctor`, `serve`, `mcp`, `build`, `check`, `test`, `lint`, `format`. Three different naming conventions for one command surface.

## Decisions already made

These are settled requirements, not options to be debated in the spec:

- The tool gets a real CLI entry point: a `bin` named `agent-flows`, with verbs. Documentation teaches this from then on.
- One targeting rule for every verb and every surface: the project is the current working directory, and `AGENT_FLOWS_PROJECT_DIR` overrides it when set. No verb may have its own rule.
- The daemon must resolve the canon directory per request rather than once at startup, so installing or editing a workflow takes effect without a restart.
- One status vocabulary shared by the HTTP API, the MCP tools, and the web page.
- A rejected gate is a normal outcome with its own terminal status, distinct from a failure.
- n8n configuration is managed from the UI; environment variables take priority over stored configuration.

## Design

**A. CLI entry point via bash shim + tsx, not a compiled build step.** The entry point is a committed bash shim at `bin/agent-flows` (modelled on `scripts/mcp-serve.sh`) that captures cwd, forces Node 22 via nvm, and execs `tsx src/cli.ts "$@"`. This avoids requiring a `pnpm build` step before the first command and keeps the entry point consistent with how all other scripts in this repository run. The thin TypeScript router at `src/cli.ts` dispatches verbs to the appropriate action. Verbs that need a daemon (like `mcp` when not running from a user project) error loudly on daemon unavailability rather than silently starting their own.

**B. Per-request canon resolution as the load-bearing decision.** F2's surprise — "I installed a workflow and the daemon ignored it" — stems from resolving the canon directory once and caching it. Per-request resolution makes the cache explicit and short-lived: if needed for performance (multiple requests per second to the same daemon), the cache is scoped to a single request context or flushed on a predictable interval (e.g., every 5 seconds). The simplest implementation fetches the directory path fresh and re-globs `<dir>/pipelines/*.yaml` per request if the directory changes. This trades a small amount of stat/glob overhead (acceptable on a single-user daemon) for correctness: the user's mental model ("I edit my pipeline, the daemon sees it") is now correct.

**C. Status rename is clean, not deprecated.** `suspended` → `awaiting_approval` uses the owner's own terminology (from the chat system documentation) and is more descriptive. `success` → `succeeded` aligns with English grammar (past-tense adjective). Both are additive to the internal Mastra workflow snapshot (which may still use Mastra's names), so only the HTTP and MCP contracts change. The run record itself may keep the Mastra status internally and translate on output (see Design A Pattern: internal schema, external contract). A review of all three surfaces (HTTP, MCP, web) is required to find and fix any remaining bare `suspended` or `success` strings.

**D. n8n configuration UI with secure storage.** The `GET /api/n8n/status` endpoint returns `{ configured: boolean, baseUrl? }` (see `src/serve/routes/n8n.ts`). The UI calls this on page load to determine the configured state. When unconfigured, the header shows an ACTION to open a configuration form; when configured, it shows the status and optionally a disconnect action. Configuration data (`~/.agent-flows/n8n.json`) is stored with file mode 0600 and never includes the API key in any response, error message, or log. Environment variables are checked first; when set, the UI shows "configured via environment variables" and disables the form.

**E. One rule for targeting: simplicity over flexibility.** Having two rules (environment variable + cwd) meant the user had to learn and remember both. One rule ("env overrides cwd") is memorable and unambiguous. No verb gets an exception because an exception would be worth learning, and there are seven verbs — learning an exception for one is a trap.

## Migration

Every place in the repository that names an old command or status string must change:

1. **pnpm scripts** (`package.json`): Remove or rename `doctor` (F1's fix). Rename all `*:*` scripts if the CLI verbs are the new primary interface.
2. **README** (`README.md`): Update setup and usage sections; show `agent-flows serve`, `agent-flows doctor`, etc., not `pnpm serve`, `pnpm run doctor`. Update the targeting rule documentation to reflect FR-003.
3. **Other specs** (`specs/**/spec.md`): Any spec that names `pnpm flows:install`, `pnpm canon:check`, `pnpm bindings:claude`, or `suspended`/`success` status strings must be updated to use the new names. Search for: "pnpm flows:", "pnpm canon:", "pnpm bindings:", "suspended", "success" (when referring to run status).
4. **HTTP server and MCP bindings** (`src/serve/server.ts`, `src/bindings/mastra/server.ts`, `src/runtime/runService.ts`): Update status enums/unions and all type definitions to use `awaiting_approval`, `succeeded`, `rejected` instead of the old names. Implement `POST /api/n8n/configure` and `DELETE /api/n8n/configure` endpoints (see `src/serve/routes/n8n.ts`), both with secure storage in `~/.agent-flows/n8n.json` (mode 0600), no API key in any response or error, and environment variable priority override.
5. **Web UI** (`src/serve/ui.html`): Replace any bare `suspended`/`success` status comparisons and strings with the new names. Implement n8n configuration form (modal or inline), connect/disconnect actions, and conditional rendering of "Edit in n8n" buttons (disabled when unconfigured, enabled and functional when configured). Display "n8n: configured via environment variables" when env vars are set and the form is disabled.
6. **Tests** (`src/**/*.test.ts`): Any test that asserts on a status string must be updated. Tests that mock HTTP responses must use the new status names.
7. **Generated binding output** (if any TypeScript/Python/JS client SDKs are auto-generated): The output must reflect the new status names. Verify that generation code reads from the source-of-truth (the spec or server code) and regenerate.
8. **Error messages and logs** (`src/**/*.ts`): Any user-facing error message naming an old verb must be updated (e.g., "run `pnpm flows:install`" → "run `agent-flows install`").
9. **CI/CD and scripts** (`scripts/`, `.github/workflows/`): Any build or test script that invokes a pnpm verb must be updated if that verb is being renamed. Keep internal pnpm scripts for development (e.g., `pnpm build` for building the CLI itself).
10. **Documentation files** (`docs/`, if any): Search for command examples and old status names.

## Verification

Every item below can genuinely pass AND fail:

1. **`agent-flows doctor` always works.** Invoke `agent-flows doctor` from any directory (not `pnpm doctor`, not `pnpm run doctor`). It prints the 13-line preflight report and exits 0. No help text, no "command not found", no silence. Repeat from three different directories to confirm it is not cwd-dependent.

2. **Installed workflows take effect without restart.** Daemon running with an empty project (0 workflows in `.agent-flows/pipelines/`). `GET /api/pipelines` returns only the 11 bundled pipelines. Then, in the project directory, run `agent-flows install spec-creation`. `GET /api/pipelines` still returns 11. Run `agent-flows install --overwrite-installed spec-creation` (or the real install flag name) to copy into the project. `GET /api/pipelines` NOW returns 12 (the 11 bundled + 1 project). The daemon log shows a state transition from "pipelines from bundled" to "pipelines from project" (or equivalent) on the second request, not requiring a restart. Verify the pipeline def returned in the 12-item list is the project's copy, not the bundled one (e.g., check a custom field or timestamp if workflows are versioned).

3. **One targeting rule, applied everywhere.** Daemon A running with `AGENT_FLOWS_PROJECT_DIR=/project-a`. Daemon B running with cwd=/project-b (no env var). Run `agent-flows install foo` in project-c's directory with no env var set — the tool installs to project-c. Run it again with `AGENT_FLOWS_PROJECT_DIR=/project-d` set — it installs to project-d, even though you are in project-c. Same behavior for `agent-flows list`, `agent-flows validate`, `agent-flows serve`. The rule is consistent across all verbs.

4. **Status strings unified across three surfaces.** Spin up a run that requires a gate approval. Observe the three surfaces simultaneously: (a) `GET /api/runs/:id` returns `status: "awaiting_approval"` (not `suspended`); (b) the MCP `run_pipeline` tool polling returns `status: "awaiting_approval"` in the same response; (c) the web UI shows the same status label. Then approve the gate. All three surfaces report `status: "running"` (not changed). Then finish the run successfully. All three report `status: "succeeded"` (not `success`).

5. **Gate rejection is an outcome, not an error.** A run reaches an auto-mode gate. The judge returns a rejection. Observe: `GET /api/runs/:id` returns 200 (not 4xx) with `status: "rejected"` and `error` containing "rejected"; the MCP polling returns `{ runId, status: "rejected" }` (not an `error` field); the web UI shows the run with terminal status `rejected` and displays the rejection reason without showing an error icon.

6. **n8n configuration from the UI and environment variable priority.** (a) Start the daemon with `~/.agent-flows/n8n.json` absent (unconfigured). Load the web UI. Observe: "Edit in n8n" buttons are visibly disabled beside each workflow; the header shows an ACTION (button/link) to configure n8n, not a passive label. Click the action, fill the form with a valid https URL and API key, submit. Observe: `POST /api/n8n/configure` returns 200 with `{ configured: true, baseUrl }` (no API key in response). The stored file `~/.agent-flows/n8n.json` has mode 0600 and contains the baseUrl and apiKey. Reload the page; the "Edit in n8n" buttons are now active and clickable. (b) Test environment variable priority: set `AGENT_FLOWS_N8N_URL` and `AGENT_FLOWS_N8N_API_KEY` in the environment. The header displays "n8n: configured via environment variables" and the configure form is disabled (grayed out, non-functional). (c) Test disconnect: click a disconnect action in the UI, observe `DELETE /api/n8n/configure` returns 200 with `{ configured: false }`, and the buttons return to disabled state. (d) Test validation: submit the configure form with an invalid URL (not http/https), observe a 400 or 422 response with a clear validation error. (e) Verify no API key appears in any response body, log line, or error message from either endpoint.

7. **CLI verbs are single tokens, no ambiguity.** `agent-flows validate` (not `agent-flows canon:check`, not `agent-flows canon validate`). `agent-flows list` (not `agent-flows flows:list`). `agent-flows generate claude` (not `agent-flows bindings:claude`). Help text and all user docs use only the single-token form.

8. **No stale MCP-to-HTTP disagreement.** The MCP `list_pipelines` tool (re-reads disk) and the daemon's internal cache for `GET /api/pipelines` resolve to the same set. Install a workflow, wait for the MCP list to refresh (if it has a cache), and verify both surfaces return the same pipeline count and ids.

9. **Error messages teach the new commands.** Any user-facing error in the daemon or CLI that names a command (e.g., "to install workflows, run...") must show `agent-flows install`, not `pnpm flows:install`. Grep for "pnpm" in error strings and user-facing output; none should remain.

10. **HTTP status enums match the MCP schemas.** Read the auto-generated OpenAPI/JSON schema for the HTTP API and the MCP tool output types. Both name the same set of status values. A runtime schema validation (if the tool performs any) against a `GET /api/runs/:id` response or MCP tool output must pass.

## Out of scope

- Run cancellation (spec 026 owns stopping a run mid-execution).
- Run persistence across restarts or recovery from crashes.
- n8n execution visibility or stop controls (spec 026 addresses visibility; stopping an n8n execution is n8n's own UI).
- Hot-reloading of pipelines after install without a daemon restart (the install-requires-restart limitation is accepted).
- Richer configuration UI or verb subcommands beyond those listed in FR-002.
- Deprecation path for old commands (break cleanly, not gracefully).

## Test plan

1. **CLI routing — each verb reaches its target.** For each verb in FR-002, invoke it with `--help` or invalid args and confirm an error message from the intended action (e.g., `agent-flows serve` with invalid args errors from daemon code, not a generic "command not found").

2. **Canon resolution per-request.** Install a workflow to a project's `.agent-flows/pipelines/` while the daemon runs. Assert `GET /api/pipelines` returns the installed set on the next request without daemon restart. Verify by checking pipeline count before and after install.

3. **Targeting rule — cwd + env override.** (a) No env var, cwd=/project-a: `agent-flows list` lists project-a's pipelines. (b) Same, but set `AGENT_FLOWS_PROJECT_DIR=/project-b`: `agent-flows list` lists project-b's pipelines. (c) Verify error handling when the directory does not exist.

4. **Status strings in all three surfaces.** Programmatically run a full gate cycle: start, wait for suspend, observe status string in HTTP API, MCP poll, and web page UI (via Playwright or headless browser). Assert they match. Reject the gate; assert all three report `rejected`. Approve and finish; assert all three report `succeeded` or `running` as appropriate to the lifecycle.

5. **Gate rejection is 200, not 4xx.** POST to `/api/runs/:id/approve` with rejection payload. Assert HTTP response is 200 (not 400/409/5xx), body contains `status: "rejected"`, and no `error` top-level field.

6. **n8n visibility toggle.** Unconfigured: render the web page, inspect the HTML for "Edit in n8n" button — it is absent. Configure n8n in the config file. Restart the daemon. Reload the page. Assert the button is present and clickable.

7. **Verb help and docs.** `agent-flows doctor --help`, `agent-flows install --help`, etc. — each must return a help message from the verb. No stale "pnpm doctor" or "pnpm run doctor" in the help text.

8. **No pnpm command in user-facing output.** Run the daemon, trigger an error that names a command to the user (e.g., "workflow not found, try running..."), and confirm the message says `agent-flows <verb>`, not `pnpm`. Grep all error messages and strings in the HTTP response bodies for "pnpm" — should return zero results in user-facing code.

9. **Backward compatibility validation.** A client written against the old HTTP API using `suspended` status string: update a minimal client to the new string `awaiting_approval` and verify it works. (This is not a forward-compatibility test; the old string is simply wrong now.)
