# 023. Trustworthy build loop

| Field        | Value                        |
| ------------ | ---------------------------- |
| Feature Name | Trustworthy build loop       |
| Branch       | `023-trustworthy-build-loop` |
| Status       | Draft                        |
| Created      | 2026-09-07                   |

> **Note:** FR-001 and FR-002 (per-step duration limits) are superseded by `specs/024-progress-watchdog/spec.md`. The owner requires that steps run with **no duration limit** — a local model may legitimately need hours — with liveness guarded instead by a progress watchdog: event-stream silence, loop detection, and a cost ceiling. The rest of this spec (the convergence command, its portability, and partial-state reporting) stands unchanged.

## Context

A supervised `cycle-dev` run against a sandbox copy of this repo (implementing `specs/016-provider-profiles/spec.md`) reached `build.develop.implement`, wrote real code, and died with `StepTimeoutError: Step timed out after 600000ms`. Three distinct defects fell out of that one failure; all claims below re-verified against the working tree 2026-09-07.

1. **Every step shares one 10-minute deadline.** `DEFAULT_STEP_TIMEOUT_MS = 600_000` (`src/canon/runStep.ts:18`). The canon already carries both override levers — `StepDef.timeoutMs` (`src/canon/types.ts:50`) and `PipelineDef.defaultTimeoutMs` (`types.ts:170`) — and the runtime already resolves precedence step > pipeline > built-in (`runStep.ts:645-646` for llm, `:540-541` for check, threaded by `src/bindings/mastra/buildSteps.ts:116-117`). But a grep of `pipelines/` for `timeoutMs|defaultTimeoutMs` returns nothing: no shipped pipeline sets either. A `scout` survey and a full multi-file implementation get the same deadline, and the deadline was sized for "a reasoner-role step on a large prompt" (`runStep.ts:12-16`) — not for a write step.

2. **A timed-out write step leaves partial, broken state and nothing says so.** The killed `implement` step left 6 changed files, ~200 insertions, and a new file in the sandbox; that state did not compile (`pnpm typecheck`: 3 errors). The run's failure surface — `RunRecord.error`, set at `src/runtime/runService.ts:151-152` and `:273`, returned as `error` from `GET /api/runs/:id` (`runService.ts:182`, route at `src/serve/server.ts:692`) — carried only `StepTimeoutError: Step timed out after 600000ms` (`runStep.ts:111`): no step id, no mention that the workspace was left dirty and unbuildable.

3. **The loop's convergence signal does not typecheck.** `pipelines/build-round.yaml:8` and `pipelines/test.yaml:10` both run `command: pnpm test`, which is `bash scripts/test.sh` (`package.json:12`) — the test runner only. Measured on the exact partial state above: `pnpm test` reported **613 passing / 0 failing** while `pnpm typecheck` reported **3 errors**. So `until: test.passed` (`pipelines/build.yaml:18`) is satisfiable by code that does not compile, and `converge` declares the build converged. The repo already defines the full gate — `"check": "pnpm lint && pnpm typecheck && pnpm format:check && pnpm test"` (`package.json:15`) — the loop never calls it. This is the failure class this project has repeatedly named: a green signal that cannot fail for the right reason. `test.yaml:8-9`'s own comment ("Parameterising it per-project is future work") marks the second half of the problem: the command is baked into shared canon that the owner intends to run across roughly ten repositories, not all of them pnpm.

Two structural facts constrain the design, both verified:

- **Check commands are never interpolated.** `buildCheckStep` passes `step.command!` verbatim to `runCheckStep` (`buildSteps.ts:364`); `renderPrompt` runs only on prompts (`buildSteps.ts:147`), and load-time placeholder validation covers prompts only (`src/canon/load.ts:362-376`) — a command is checked only for presence (`load.ts:171-172`).
- **`defaultTimeoutMs` does not survive nesting.** `kind: pipeline` steps expand at load time by inlining child steps into the parent def, and `load.ts` contains zero occurrences of `timeoutMs` (grep, 2026-09-07) — the child's `defaultTimeoutMs` is silently discarded; the builder reads only the compiled def it is given (`src/bindings/mastra/build.ts:101,141`). Per-step `timeoutMs` travels on the `StepDef` itself and survives expansion.

## Functional Requirements

| ID     | Requirement                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| FR-001 | The long steps get explicit per-step deadlines via the existing `StepDef.timeoutMs` (`types.ts:50`) — a data-only change, no runtime code: `develop.yaml` `implement` → `timeoutMs: 3600000` (60 min); `build-round.yaml` `fix` → `timeoutMs: 1800000` (30 min); `build-round.yaml` `test` and `test.yaml` `run` → `timeoutMs: 900000` (15 min). `PipelineDef.defaultTimeoutMs` is deliberately NOT used anywhere (Design, decision A).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| FR-002 | `DEFAULT_STEP_TIMEOUT_MS` stays `600_000` (`runStep.ts:18`). Every step not named in FR-001 — `investigate.survey`, `investigate.findings`, `intake`, `enrich`, `critic`, `security`, all `audit` steps, `correct-plan` — continues to inherit it unchanged.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| FR-003 | The convergence command becomes a property of the target project: an optional file `<projectDir>/.agent-flows/config.json` with shape `{"checkCommand": "<shell command>"}`. The daemon reads it exactly once at startup, where it already resolves `projectDir` and builds all workflows (`server.ts:949-951,986`), and threads the value through `BuildDeps` (`buildSteps.ts:22-30`). When the file or key is absent, the default is `pnpm lint && pnpm typecheck && pnpm format:check && pnpm test` — matching the project's own `check` script in `package.json` exactly. The default must mirror that script: a gate weaker than the project's real gate can converge on code the project rejects. This was confirmed by a live self-run (2026-09-07) that produced a refactor with passing tests and clean typecheck but failing `format:check`; the old default (`pnpm lint && pnpm typecheck && pnpm test`) declared that run converged. Malformed JSON is a loud startup error naming the file, not a silent fallback. |
| FR-004 | A check step's `command` may contain exactly one recognised placeholder, `{{checkCommand}}`, substituted at build time from FR-003's config-or-default — never from run context. Load-time validation: any other `{{...}}` occurrence in a `command` is a load error naming the step and the placeholder. Run context (pipeline inputs, step outputs) cannot influence the substituted value by construction: substitution happens in `buildCheckStep` before any run exists, from `BuildDeps` only. Commands containing no placeholder are untouched.                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| FR-005 | `build-round.yaml:8` and `test.yaml:10` both change from `command: pnpm test` to `command: "{{checkCommand}}"`. The loop wiring is otherwise untouched: the check step keeps id `test`, `until: test.passed` (`build.yaml:18`) and `maxIterations: 3` (`build.yaml:13`) are unchanged — only what "passed" measures changes.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| FR-006 | `**/.agent-flows/**` is added to `BUILD_CONFIG_DENY_PATTERNS` (`runStep.ts:98-105`) — Edit denied, Read allowed, same as the other entries. Without this, a `contents: write` step (e.g. `build-round.fix`, `build-round.yaml:15-16`) could rewrite `.agent-flows/config.json` or an installed pipeline mid-run — the exact attack the pattern list already names for `package.json` ("a step rewriting `test` to `echo PWNED` is the attack", `runStep.ts:92`). FR-003's read-once-at-startup rule independently closes the same hole for the current run; this closes it for the next one.                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| FR-007 | Every step failure error names the failing step. `buildLlmStep` wraps errors thrown by the runner as `Step "<step.id>": <original message>` — the prefix convention already used for schema failures (`buildSteps.ts:201`). A timeout therefore surfaces as `Step "build.develop.implement": StepTimeoutError: Step timed out after 3600000ms` through the existing unchanged path: `runService.ts:270-274` formats it, `:151-152` records it, `:182` returns it from `GET /api/runs/:id`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| FR-008 | When a step with `permissions.contents: write` fails for any reason (timeout included), the binding appends the workspace state to the FR-007 error before rethrowing: the daemon (not a sandboxed step) runs `git status --porcelain` in `deps.cwd` and appends `Workspace may contain partial writes: <first 20 lines, then "…and N more">`. If the directory is not a git repository: `Workspace may contain partial writes; not a git repository, dirty-file listing unavailable.` Node's `child_process` only — no new dependencies.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| FR-009 | The system NEVER modifies the workspace in response to a failure: no `git checkout`, no revert, no stash, no file deletion. Partial state is left exactly as the killed step left it and is made discoverable via FR-007/FR-008 through `error` on `GET /api/runs/:id` (`runService.ts:86,182`) — the string shape of `GetResult.error` is unchanged, so SSE and MCP surfaces inherit the enriched message for free.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |

## Design

**A. Per-step `timeoutMs`, never `defaultTimeoutMs`, and the built-in default stays put.** The pipeline-default lever looks natural but is a trap in this canon: nested expansion inlines child steps into the parent def and drops the child's `defaultTimeoutMs` (`load.ts` has zero `timeoutMs` occurrences; `build.ts:101,141` reads only the compiled def). A `defaultTimeoutMs` on `develop.yaml` would apply when `develop` runs standalone and silently vanish when it runs nested inside `build` inside `cycle-dev` — which is exactly how the failing run invoked it. Per-step values travel on the `StepDef` through expansion and are self-documenting at the step they govern. The numbers: the killed `implement` had produced ~200 insertions at the 10-minute mark, so 10 minutes is demonstrably inside the working range of a real implementation; a write-step timeout converts work into hazard (defect 2), so write steps get the most generous ceilings compatible with the existing constraint that "a wedged CLI does not hold a daemon slot for a working day" (`runStep.ts:14-15`) — 60 min for `implement` (full spec implementation, unbounded scope), half that for `fix` (scope bounded to repairing a failing gate). The gate check steps get 15 min: the gate grows from test-only to lint+typecheck+test (FR-003) and must fit ten different repos' suites with cold caches; deterministic commands that run longer than 15 minutes are a project problem, not a harness one. `DEFAULT_STEP_TIMEOUT_MS` itself is unchanged: it was sized for reasoner steps (`runStep.ts:12-16`) and the inheriting population (FR-002) is exactly that; moving the global default to fit two write steps would mis-size the other twelve, and the two are now sized explicitly.

**B. The gate: `lint && typecheck && format:check && test`, resolved from project config — the load-bearing decision.** Three sub-decisions, argued:

- _`format:check` is included in the default._ The original spec excluded it on the grounds that the `fix` step is an LLM with no shell access, so a prettier failure would waste an iteration on whitespace. That reasoning was tested by a live self-run (2026-09-07): the run produced a refactor whose tests passed and typecheck was clean, but `pnpm check` (the project's own gate) failed because three files were unformatted. The old default declared that run converged — the exact defect class this spec exists to prevent. The fix step cannot format mechanically, but the gate's job is to report the truth: if the project rejects the code, convergence must not be declared. A project where the fix step truly cannot address formatting can set `checkCommand` without `format:check` via config — the mechanism makes this one line, not a canon fork.
- _Project config file, not a pipeline input._ A pipeline input was rejected on three grounds. First, the check command is a fact about the repository, not about a run — forcing the operator to pass it on every chat trigger misplaces it, and threading it from `cycle-dev` through `build` through the loop body would touch every composition. Second, `with:` rewrites prompt placeholders only (`types.ts:137-144`) and commands are never rendered (`buildSteps.ts:364`), so input-threading needs new interpolation machinery anyway. Third — decisive — values reaching `command` reach `/bin/sh -c`, and run context includes LLM step outputs; the repo's entire check-step hardening (`CHECK_ENV_ALLOWLIST`, `BUILD_CONFIG_DENY_PATTERNS`) exists to keep model-influenced data away from the shell. FR-004's build-time-from-config-only substitution keeps that wall intact; FR-006 stops a write step from reaching around it via the config file. The other rejected alternative — "each project edits its installed copy of `build-round.yaml`" — technically works today (project canon wins resolution) but forks the whole pipeline per repo and guarantees drift across ten repositories over one string.
- _Default-with-override, not mandatory config._ When config is absent the default runs. In a non-pnpm repo without config the check fails loudly (`pnpm: command not found` lands in `CheckResult.output`, `runStep.ts:589`) and the loop reports non-convergence — wasteful (up to three no-op fix calls) but visible and honest. The rejected strict mode (startup error when config is absent) punishes every pnpm repo including this one to protect misconfigured ones; the failure mode it prevents is already loud. Read-once-at-startup is stated behaviour: changing `checkCommand` requires a daemon restart, which is both the honest consequence of workflows being built at startup (`server.ts:986`) and a security property (a mid-run config edit changes nothing).
- _`test.yaml` changes too._ A standalone pipeline whose result says `passed: true` against a weaker gate than the loop's would be a second copy of defect 3; its own comment already calls the hardcoding future work (`test.yaml:8-9`). One gate definition, used everywhere.

**C. Partial state: leave it, and say so loudly.** Three options were on the table. Automatic revert/checkout is rejected outright: the killed step's writes may include an hour of salvageable work, and destroying the operator's workspace to make a report cleaner is strictly worse than any reporting gap. Silent leave-in-place is the status quo and produced defect 2. The choice is leave-and-report: FR-008 embeds the `git status --porcelain` listing in the error string at the moment of failure — captured by the daemon, which is not sandboxed, in the same `deps.cwd` the step wrote to — and FR-009 carries it to `GET /api/runs/:id` with zero changes to `RunService`, because `record.error` already flows there (`runService.ts:151-152,182`). Keeping `error` a string (not a structured dirty-files field) is deliberate minimalism: every existing consumer (HTTP, SSE, MCP, UI) renders it today, and a structured field can be added later without unsaying anything. The listing is capped at 20 lines because `git status` output is unbounded and the error string travels in API responses.

## Backward compatibility

- FR-001 is data-only: the timeout fields and their precedence chain already exist and are tested (`build.test.ts:778-850`); no schema or runtime change. Pipelines without `timeoutMs` behave exactly as today (FR-002).
- FR-004 changes load-time behaviour only for commands containing `{{...}}` — today such a string is passed literally to the shell (`buildSteps.ts:364`) and no shipped or plausible project pipeline does this; commands without placeholders are byte-identical in behaviour.
- Absent `.agent-flows/config.json` → the FR-003 default. This repo converges under it today except for the gate now correctly failing on typecheck/lint errors — which is the point, not a regression.
- `until: test.passed`, step ids, loop shape, `GET /api/runs/:id` response shape, and `GetResult` are all unchanged; FR-007/FR-008 only lengthen an existing string field.
- FR-006 tightens write steps: they lose the ability to edit `.agent-flows/**` mid-run. No shipped prompt asks a step to do that; a step that needs it is the attack, not a use case.

## Out of scope

- Continuing the loop when the `fix` step itself times out (treating a fix timeout as a failed iteration rather than a failed run) — a loop-semantics change, worth its own spec.
- Automatic retry of timed-out steps, and checkpointing/resuming a partially-written implementation.
- Any automatic workspace cleanup, revert, or stash (explicitly rejected, FR-009).
- Per-project timeout overrides in `config.json` — per-step yaml values suffice until a second project proves otherwise.
- A `doctor` check that validates `checkCommand` against the target repo.
- Renaming `build-round`'s `test` step to `check` (would touch `until` wiring for zero behaviour).
- An automated formatting pass inside the loop; formatting remains a `ship`-time concern.

## Test plan

1. **Convergence rejects code that passes tests but fails typecheck — FAILS today; this case is the point of the spec.** Fixture project: a passing trivial test script and a TypeScript file with a deliberate type error; `checkCommand` resolves to a gate that includes typecheck. Build the `build` workflow against the fixture with a stubbed llm runner (no-op `fix`), run the `converge` loop: the check step's result has `passed: false` and the loop outcome (`buildSteps.ts:426-437`) reports `converged: false` after `maxIterations`. Run the same fixture through today's `command: pnpm test` wiring to pin the inversion: today it converges, proving the old gate could not fail for the right reason.
2. **`checkCommand` resolution.** Config present → the configured command runs (command writes a marker file; assert it exists). Config absent → the default string is what `runCheckStep` receives (spy via injected `spawn`). Malformed config JSON → startup error naming the file. A run-context key named `checkCommand` (as pipeline input and as a step output) has no effect on the executed command.
3. **Placeholder validation.** A check step with `command: "{{other}}"` → load error naming the step and `other`; `command: "echo {{checkCommand}} {{other}}"` → same; a literal command with no braces loads and runs unchanged.
4. **Timeout wiring is data-complete.** Load bundled `develop.yaml`, `build-round.yaml`, `test.yaml`: the FR-001 steps carry exactly the specified `timeoutMs` values and they reach the runner deps (captured-deps pattern of `build.test.ts:778-850`). Load `spec-creation.yaml` and `audit.yaml`: no step carries `timeoutMs` (FR-002 regression guard).
5. **Dirty-workspace failure report.** Fixture git repo; stubbed runner throws `StepTimeoutError` from a `contents: write` step after a file is modified: `GET /api/runs/:id` returns `status: "failed"` and an `error` containing the step id, `timed out`, and the modified file's path. Same fixture in a non-git temp dir → the documented "not a git repository" sentence.
6. **No-revert guarantee.** After case 5, the modified file's bytes are identical before and after failure handling — the daemon read the workspace state but wrote nothing.
7. **`.agent-flows` edit-deny.** With `contentsAccess` set, the constructed `--disallowedTools` value contains `Edit(**/.agent-flows/**)` and does not contain `Read(**/.agent-flows/**)` (assert against the args captured by the injected spawn, alongside the existing pattern tests).
8. **Step id end-to-end.** A timeout in a non-write llm step surfaces through `waitForSettled` and `GET /api/runs/:id` as `Step "<id>": StepTimeoutError: …` with no workspace suffix — FR-007 applies to every step, FR-008 only to write steps.
