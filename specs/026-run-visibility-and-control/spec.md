## Context

The owner's requirement, verbatim: _"я як користувач маю бачити усі процеси які йдуть через нашу тулзу, або через наш юай або через н8н … маю мати можливість бачити прогрес і зупинити … маю легко розуміти як розпочати роботу над новим проектом і почати розробку"_ — three requirements: (1) see EVERY process running through this tool, whether started from our UI, chat, or n8n; (2) watch progress and be able to STOP a run; (3) an obvious path from an empty project directory to a first running pipeline. All claims below re-verified against the working tree 2026-09-07.

1. **There is no way to stop a run.** A repo-wide grep for cancel/abort/stop (2026-09-07) finds no run-level path: `RunService` exposes `start`/`waitForSettled`/`get`/`list`/`approve`/`subscribe` only (`src/runtime/runService.ts:222-819`), and the daemon's run routes are `POST /api/runs` (`src/serve/server.ts:641`), `GET /api/runs` (`:679`), SSE (`:687`), `GET /api/runs/:id` (`:738`), approve (`:753`), and gate-judge (`:779`). Spec 020 explicitly deferred this: "Cancelling/killing a run from the UI" is in its Out of scope (`specs/020-run-observability/spec.md:63`). Today a runaway run ends only when the daemon dies.

2. **Step-level abort machinery already exists end-to-end — nothing feeds it per-run.** `StepRunnerDeps.signal?: AbortSignal` (`src/canon/runStep.ts:150`); `createDeadline(timeoutMs, parentSignal)` propagates a parent abort into the step deadline signal (`runStep.ts:296-326`, propagation `:310-322`); on abort the claude transport SIGTERMs the child (`src/canon/runClaudeCli.ts:386-388`, pre-start `:467-474`) and an operator abort takes priority over a watchdog trip, surfacing as `AbortError` not `StepTimeoutError` (`runClaudeCli.ts:402-405`; `runStep.ts:912-918` rethrows non-timeout aborts unchanged); check steps SIGTERM then escalate to SIGKILL (`runStep.ts:633-647`, grace `:560`) and report "Step was cancelled" (`:620-627`); the api transport aborts the fetch (`:465`) and codex exec SIGTERMs (`:544-550`). **Two gaps**: (a) the claude operator-abort path sends SIGTERM with NO SIGKILL escalation, unlike the watchdog path (`runClaudeCli.ts:291-292`, constant `:22`) — a child ignoring SIGTERM lingers; (b) the Mastra binding never threads a per-run signal: `buildLlmStep`'s execute destructures only `{ inputData }` (`src/bindings/mastra/buildSteps.ts:188`) and builds runner deps without `signal` (`:223-236`); `buildCheckStep` likewise (`:463-469`).

3. **Mastra 1.63.2 (`package.json:31`) provides the missing link.** `Run.cancel(): Promise<void>` exists (`node_modules/@mastra/core/dist/workflows/workflow.d.ts:534`) and every step `execute` receives `abortSignal: AbortSignal` in its params (`workflow.d.ts:404`, `step.d.ts:48`); Mastra's own run-status vocabulary includes `'canceled'` (`types.d.ts:211`). **Unverified from types alone**: that `cancel()` on the default engine aborts the in-flight step's `abortSignal` — the evented engine documents exactly that linkage (`evented/workflow.d.ts:136`), but the default engine's behaviour must be pinned by a test (T-1), not assumed.

4. **The race-safety pattern to reuse.** `RunService.approve` is single-flight: the guard rejects non-suspended runs (`runService.ts:397-400`) and the status transition to `"running"` happens synchronously before the first await (`:405`). `resolveGate` discards a judge verdict arriving after the run left `suspended`, recording it `superseded` (`:522-527`). `settle` is a resolve-once promise (`:254-257`), so settling twice is a harmless no-op.

5. **Chat-started and UI-watched runs are already one registry — requirement (1) holds for our own surfaces.** The MCP binding proxies every run tool to the daemon over HTTP (`src/bindings/mastra/server.ts:21-38`): `run_pipeline` POSTs `/api/runs` and polls `GET /api/runs/:id` (`:99-136`), `approve` and `get_run` proxy likewise (`:150`, `:178`). Verified: a chat run lands in the daemon's registry and appears in `GET /api/runs` and the UI.

6. **n8n executions are invisible.** No reference to n8n's executions API exists anywhere in `src/` (grep 2026-09-07). What exists: config at `~/.agent-flows/n8n.json` re-read on every call with env overrides (`src/serve/routes/n8n.ts:19`, `:36-52`), the `fetchN8n` client attaching `X-N8N-API-KEY` (`:86-91`) under the standing rule that the key NEVER appears in any response, error, or log (`:16-18`, `:81-85`), `GET /api/n8n/status` (`server.ts:1156-1164`), a workflow-list proxy (`:1167-1185`), and the project map `<projectDir>/.agent-flows/n8n.json` of pipelineId → n8nWorkflowId written by the push route (`server.ts:97-115`, `:1188-1259`). **Not verified today**: n8n's public-API executions surface itself — docs.n8n.io returned 404s to every fetch attempted 2026-09-07 and the OpenAPI paths are in unfetchable `$ref` files. Working assumption from prior knowledge, which implementation MUST confirm against the target instance's own `/api/v1/docs` playground: `GET /api/v1/executions` (filterable, historic executions), `GET/DELETE /api/v1/executions/{id}`, and NO public stop/cancel endpoint. The design below does not depend on stop existing; if listing running executions turns out unsupported, the honest degradation is stated in Design D.

7. **Runs do not survive a daemon restart — by design, and requirement (1) survives it.** Spec 020 FR-008 (`specs/020-run-observability/spec.md:35`) and its Design (`:46`): a restart kills the background `run.start()` promise and the child step processes, so a post-restart "in-flight" entry would be a lie. This spec keeps that posture: requirement (1) means live visibility of live processes, and every live process dies with the daemon. What is genuinely lost is completed-run _history_; the n8n side has no such gap (n8n persists its own execution log independent of our daemon). A read-only history view over Mastra's LibSQL snapshots is flagged as a future recommendation, not designed here.

8. **What the UI shows today.** Active Runs is the first section (`src/serve/ui.html:398-405`) with a 4-second poller (`:884-898`), a suspended-runs approval banner (`:840-846`), attach-with-SSE (`:865`, `:904-961`), and gate Approve/Reject in the detail panel (`:974-1037`); `statusClass` already styles `"cancelled"` (`:822-828`). **Missing**: no stop control anywhere; no way to START a run — the project tier's only actions are View / Edit in n8n / Delete (`:583-587`) and the only `POST /api/runs/...` calls in the file are the two approve calls (`:1014`, `:1028`); the header shows only the n8n badge, not which project the daemon is serving (`:385-393`).

9. **Onboarding machinery exists; the flow does not.** `installWorkflow`/`listAvailable`/`listInstalled` (`src/install/install.ts:75-140`), `POST /api/install` (`server.ts:810-846`), `GET /api/environment` returning `projectDir`, `pipelinesSource`, installed and available lists (`:849-894`), template install (`:1117-1150`). The daemon learns the project directory from `AGENT_FLOWS_PROJECT_DIR` (falling back to cwd, loud failure on a nonexistent dir — `src/bindings/mastra/projectDir.ts:21-36`; set by `scripts/dev-serve.sh:8-9`). On a fresh project `resolveCanonDir` falls back to the bundled catalog (`server.ts:1279-1281`), so all 11 bundled pipelines (glob of `pipelines/*.yaml`) are loadable and runnable with zero installation. **Wrinkle**: workflows are built exactly once at startup (`server.ts:1318-1331`), so installing project copies mid-session changes nothing until the daemon restarts. A newcomer opening the UI sees "No active runs" (`ui.html:836-838`), "No workflows installed in this project." (`:572-574`), and Install buttons (`:719-744`) — no guidance and no runnable affordance. The settled division stands: the UI is the inventory and monitor, n8n is the authoring surface (`README.md:119`); starting a run is not authoring.

10. **Partial-state precedent.** Spec 023 FR-008/FR-009 (`specs/023-trustworthy-build-loop/spec.md:38-39`): on write-step failure the binding appends a daemon-captured `git status --porcelain` listing to the error (`buildSteps.ts:39-54`, `:246-252`) and the system NEVER reverts the workspace. A cancelled write step is the same situation and gets the same treatment.

## Design

**A. Cancel is `RunService` orchestrating the abort chain that already exists — the load-bearing decision.** Two mechanisms were on the table. (1) _Daemon-side process tracking_: record child PIDs per run and kill them directly. Rejected: it invents a second kill mechanism parallel to the one the runners already own — the deadline/signal chain with its SIGTERM→SIGKILL escalation, transport-specific handling (fetch abort for api, stdin-fed claude, codex exec), and the abort-vs-timeout priority rule (Context §2) — and it would bypass Mastra, leaving the workflow believing the step is still running. (2) _`run.cancel()` + per-invocation signal threading_: Mastra already hands every step execute an `abortSignal` (Context §3); threading it into `deps.signal` is a two-builder change (FR-003) after which cancellation flows through code that is already tested for timeouts and watchdog kills. Committed to (2). The one uncertainty is owned explicitly: whether the default engine's `cancel()` aborts the in-flight `abortSignal` is unverified from type declarations (Context §3), so T-1 pins it with a real Mastra workflow and a hanging fake spawn — if it fails, the fallback is a run-scoped `AbortController` registry keyed at execute time, and that decision is made on T-1's evidence, not now. Note the per-run signal cannot ride `BuildDeps.runnerDeps` — deps are baked at build time and shared by all runs of a workflow (`server.ts:1318-1331`); the per-invocation `abortSignal` is precisely the run-scoped carrier.

**B. A distinct `"cancelled"` terminal status — deliberately diverging from 025's rejection of `"rejected"`.** Spec 025 folded rejection into `failed` because the gate decision already had a carrier (`gateDecisions`) and the error string told the truth. Cancellation has no other carrier: reporting an operator's deliberate stop as `failed` sends the operator hunting for a defect that does not exist, and makes "how many runs actually failed" unanswerable from the list. The surface cost is small and already half-paid: the UI styles `cancelled` today (`ui.html:827`), the unions are additive, and the MCP poller needs one branch (FR-006). Cancelling a `suspended` run is allowed — a run stuck at a gate nobody will approve is exactly the run the owner wants to kill — and needs no resume: the record goes terminal, and a later approve hits the existing not-suspended guard. Mastra's LibSQL snapshot for that run stays `suspended`; harmless, since the in-process registry is the only authority and dies with the process (Context §7).

**C. Races reuse the approve shape; nothing new is invented.** Cancel-vs-cancel: the synchronous transition means the second caller sees `"cancelled"` and gets the 409 — same-tick safe. Cancel-vs-approve: whichever transitions first wins; a cancel landing after approve's transition (`runService.ts:405`) still proceeds (the run is `"running"`, cancellable) and the in-flight resume's result is discarded by the FR-002 guard; an approve landing after cancel gets approve's own 409. Judge-vs-cancel: the superseded guard (`:522-527`) already discards the verdict; FR-002 adds only the abort (stop paying for it) and the degrade guard (don't resurrect a cancelled run as `awaiting_approval`). Partial writes: the killed step may have written files; 023 already decided leave-and-report, and FR-005 reuses its exact reporting shape — cancel gets no cleanup because _nothing_ gets cleanup in this system.

**D. n8n visibility: poll-and-link, honestly bounded.** Three options weighed. _Webhook from n8n into our daemon_: rejected — it requires editing every n8n workflow, and the daemon may be down while n8n runs, silently losing events. _Merge into `GET /api/runs`_: rejected — it fakes parity; an n8n execution has none of our run's contract (no SSE, no gate, no stop), and a unified list would imply all of it. _Daemon proxy route + separate UI section + deep links_ (FR-008/FR-009): committed. Freshness is polling-grade (~10 s), which matches the owner's need (glance: "is anything running through n8n?"); the daemon-down case is honest by construction — our UI is unreachable then anyway, and n8n's own UI, which owns the execution store, remains the complete record, so nothing is ever lost, only temporarily not mirrored. What the user can and cannot do, plainly: they can SEE recent (and, if the public API lists them, in-flight) n8n executions and jump to each one; they CANNOT stop an n8n execution from our UI — no public stop endpoint is assumed (Context §6), and the row link opens n8n's execution view where n8n's own controls live. If implementation confirms the public list excludes running executions, the section is titled as recent executions and keeps the link to n8n's live view — degraded visibility stated on the surface, not silently misrepresented. Filtering: ALL instance executions are listed (capped), with project-map annotation for ours — this is a personal instance, and n8n-authored workflows doing project work are exactly the "through n8n" processes the owner named; a mapped-only filter would hide them.

**E. Onboarding: the shortest path is already almost there — the spec adds signposts, not machinery.** The verified path: `cd <new-project> && agent-flows serve` (or `AGENT_FLOWS_PROJECT_DIR=… scripts/dev-serve.sh`) → open `http://127.0.0.1:7411` → the fresh project falls back to the bundled catalog (Context §9), so the first click is **Run** on `spec-creation` or `cycle-dev` (FR-011) — zero installs, first pipeline running, watched in Active Runs, stoppable via FR-007. The rejected alternative — a checklist card with no Run button — cannot produce a running pipeline without leaving the UI for a chat client or curl, which is precisely the "легко розуміти" failure being reported. FR-011 does not touch the settled division: authoring stays in n8n, the inventory stays here (`README.md:119`); running an already-defined pipeline is operation, not authoring. The two honest wrinkles are surfaced instead of fixed: install-requires-restart (FR-012 says the sentence; hot-reload of workflows is real machinery for another spec) and which-project-am-I-in (FR-010 puts it in the header). Chat-first remains the primary entry; nothing here changes MCP.

## Backward compatibility

- All existing routes keep their shapes; `POST /api/runs/:id/cancel` and `GET /api/n8n/executions` are new. `GetResult`/`RunSummary`/`SettledResult` gain one additive union member (`"cancelled"`); SSE and MCP consumers that switch on known statuses treat it as they treat `failed` until updated — the UI already does (`ui.html:827`).
- `GetResult.error` now also appears on cancelled runs (FR-005); it remains a plain string, so every existing consumer renders it unchanged.
- MCP: `run_pipeline`, `approve`, `get_run`, `list_pipelines` schemas are unchanged; `run_pipeline` may now return `status: "cancelled"` (previously impossible); `cancel_run` is a new tool.
- `runClaudeCli`'s operator-abort now escalates to SIGKILL (FR-004) — a behavioural tightening on a path nothing could previously trigger at run level.
- The judge runner deps gain an optional `signal` (FR-002); stubs that ignore unknown deps fields are unaffected.
- UI changes are additive sections/buttons on the existing layout; the Active Runs section, poller, banner, and gate controls are built on, not redesigned (Context §8).
- Spec 020's restart posture is unchanged: `GET /api/runs` is empty after restart, and cancelled runs vanish with the process like every other run.

## Out of scope

- Persisting runs or run history across daemon restarts, and any rehydration of Mastra LibSQL snapshots (Context §7; flagged recommendation: a future read-only history view over the existing snapshots).
- Stopping, retrying, or deleting n8n executions from our UI, and any webhook/push integration from n8n into the daemon (Design D).
- Pause/resume, per-step cancel, cancel-with-revert, or any workspace cleanup (023 FR-009 stands).
- Hot-reloading pipelines into a running daemon after install (FR-012 states the restart requirement instead).
- A gateMode selector, model overrides, or any richer run-configuration form in the FR-011 run dialog.
- Authoring or editing workflows in our UI (`README.md:119` division stands).
- Cancelling n8n-side executions of exported gate Wait-nodes (spec 025 FR-011 territory).

## Test plan

1. **Cancel aborts the in-flight step — pins the Context §3 uncertainty; gating.** Real Mastra workflow, fake hanging spawn (pattern of `runStep.test.ts:243-267`): start, wait for step-start, `cancel(runId)`. Assert: the runner's `deps.signal` aborted, the fake child's `kill` was called, `GetResult.status === "cancelled"`, `error` contains "cancelled by operator", and `settledPromise` resolved `{ status: "cancelled" }`. If Mastra's default engine does not propagate — this test is the tripwire that forces Design A's fallback.
2. **Cancel a suspended run** — gated fixture, wait for `suspended`, cancel: no `resume` call ever made (spy), status `"cancelled"`; subsequent `approve` returns the existing not-suspended error and the HTTP route 409s.
3. **Route contract** — cancel unknown id → 404; cancel a `success` and a `failed` run → 409 with the status named; cancel a running run → 200 whose body is the updated `GetResult`; second cancel → 409.
4. **Races** — (a) two cancels in the same tick: exactly one Mastra `cancel()` call, second caller errors; (b) approve then immediate cancel: run ends `"cancelled"` and the late resume result does not overwrite it (resume resolves after cancel; assert status and no double-settle); (c) cancel then approve: approve 409s.
5. **Judge interplay** — auto-mode run suspended with a slow stubbed judge: cancel mid-judge → judge deps signal aborted; a verdict the stub still returns is recorded `superseded: true` and never applied; no `degradeToManual` settle fires after cancel (run stays `"cancelled"`, `judgeError` unset).
