## Context

The owner's decision, verbatim: _"схоже на 1 але це просто гілка. якщо мануальне то очікує користувача, якщо автоматично то незалежний агент перевіряє і підповідає"_ — the approval mode is **run-level**, and the gate is **a branch**: in **manual** mode it waits for the human, as today; in **auto** mode an **independent agent** evaluates the gate material and answers in the human's place. Auto is not "skip the gate" and not "auto-approve" — the gate still receives a real judgment. The owner separately decided that in the n8n binding the gate must become a **real node**, not the NoOp it is today. All claims below re-verified against the working tree 2026-09-07.

1. **Gate mechanics.** `buildGateStep` (`src/bindings/mastra/buildSteps.ts:338-366`) suspends with `{ message, spec }` (`buildSteps.ts:358-361`) where `spec` is `ctxData[nsKey(step.id, "spec")]` — for `ship`'s gate no step ever writes that key (no `assemble` step; `pipelines/ship.yaml`), so the human is shown the message and an undefined spec; the real material is the working tree. On resume the gate writes `<gateId>.approved` into context (`buildSteps.ts:346,356`). `RunService.approve(runId, approved)` (`src/runtime/runService.ts:204-235`) resumes with `resumeData: { approved }` (`runService.ts:216-219`); a non-suspended run gets an error, never a silent no-op (`runService.ts:206-209`), and the status transition to `"running"` happens synchronously before the first await, making approval single-flight (`runService.ts:211-214`).

2. **What `approved: false` actually does today — the load-bearing defect.** Exactly two step kinds read the approved key: `persist-ticket` (`buildSteps.ts:380`) and `export-spec` (`buildSteps.ts:400`); a repo-wide grep for `approved` (2026-09-07) finds no other consumer, and check steps are wired with no gate awareness (`src/bindings/mastra/build.ts:140-141`). The workflow **continues** after a rejection. Concretely: rejecting `ship`'s gate still runs `commit` and `pr` (`pipelines/ship.yaml:18-29`) — the run commits and opens a public PR anyway; rejecting `cycle`'s plan gate still builds and ships the rejected plan (`pipelines/cycle.yaml:10-25`). Verified by code reading; no runtime reproduction was executed. Additionally, verified against the working tree 2026-09-07: `buildCheckStep(step, deps, defaultTimeoutMs)` (`src/bindings/mastra/buildSteps.ts:426-430`) takes NO gate parameter at all — a `check` step has no code path by which it could consult a gate decision. `findGateAncestor` is called at exactly two sites, `src/bindings/mastra/build.ts:118` (persist-ticket) and `:143` (export-spec). No other step kind is gate-aware. Therefore rejecting `ship`'s gate still executes `commit` and `pr` (`pipelines/ship.yaml`), whose own comment states the gate exists because those actions are irreversible. Runtime reproduction was deliberately NOT performed: it would create a real commit and a real public pull request. An auto mode whose rejection cannot stop the PR would be a check that cannot fail — this spec must close the hole.

3. **Human approval surfaces.** `GET /api/runs/:id` returns `gateMessage`/`spec` when suspended (`runService.ts:83-86,184-189`; route `src/serve/server.ts:739-754`); the SSE stream sends the same snapshot first (`server.ts:713`); `POST /api/runs/:id/approve` (`server.ts:756-783`); the MCP `approve` tool (`src/bindings/mastra/server.ts:149-166`, whose description at `:152` states "approved=false … discards it"). Latent quirk: `ApproveResult.error` is documented as "call could not be processed" (`runService.ts:72-73`) but is also set for a genuine post-resume workflow failure (`runService.ts:234`), and the HTTP route returns 409 on **any** defined `error` (`server.ts:776-780`) — so an approval whose resumed run then fails is answered 409 as if the approval itself were invalid.

4. **Run start surfaces.** `POST /api/runs` accepts `{ pipeline, inputs, models }` (`server.ts:658-690`); the MCP `run_pipeline` tool accepts the same and blocks on `waitForSettled` (`bindings/mastra/server.ts:105-147`), which resolves once, at first suspension or completion (`runService.ts:100-103,129-133,144`). Per `specs/020-run-observability/spec.md` (Draft, **not implemented**: no `GET /api/runs` list route exists in `server.ts` today), the MCP binding runs its own `RunService` in a separate process.

5. **Gates shipped today**: `spec-creation.approve` (`pipelines/spec-creation.yaml:47-50`) and `ship.approve` (`pipelines/ship.yaml:9-11`). `cycle` nests both (`cycle.yaml:10-25`), and `kind: pipeline` steps are inlined at load time into one flat workflow (verified in 023's Context; the builder refuses unexpanded pipeline steps, `build.ts:156-159`) — so one run has one context and its gates are ordinary steps of a single workflow.

6. **n8n binding.** The gate is a NoOp: `build.ts:250-252` carries the exact `TODO(binding-c): map gate to a real HITL/Wait node`; `"gate"` is in `NOOP_STEP_KINDS` (`src/bindings/n8n/build.ts:38-44`). An exported `ship.json` today would run `commit` and `pr` with the approval step doing nothing — the same defect as fact 2, in a second binding.

7. **Model roles.** The canon defines roles `reasoner`/`worker`/`scout` mapped per provider profile (`src/canon/registry.ts:65-78`); the default `anthropic` profile maps `reasoner` to `fable`, pinned to `claude-fable-5` (`registry.ts:32,68`); the `local` profile's `reasoner` is `ollama-qwen`, an **api-transport** entry (`registry.ts:38-45,75-77`), and `permissions.contents` is unsupported on api transport (`src/canon/runStep.ts:692-696`).

8. **A one-shot judged LLM call already exists as a hardened primitive.** `runLlmStep(entry, prompt, deps)` is exported (`runStep.ts:682-686`); every claude invocation gets `--restricted --strict-mcp-config` and an explicit tool allowlist unconditionally (`runStep.ts:753-775`); the 024 progress watchdog is implemented (`StepWatchdogError` at `runStep.ts:136`, digest sentinels `runStep.ts:654-655`, untrusted-data fencing `runStep.ts:662-678`) and claude-transport llm calls have **no built-in duration limit** (`runStep.ts:713-718`) — any judge built on this primitive inherits all of it.

## Design

**A. The branch lives in `RunService`, not in the gate step — the load-bearing decision.** Two placements were on the table. (1) _Gate-step branch_: in auto mode the Mastra gate step itself calls the judge and writes `approved` without suspending. (2) _Daemon branch_: the gate always suspends; `RunService`, seeing an auto run suspend, dispatches the judge and answers through the same resume path a human uses. Committed to (2), on four grounds. First, it is the most literal reading of the owner's decision — the agent "перевіряє і підповідає" (checks and answers): it answers through the human's own channel, and the Mastra binding needs zero build changes. Second, observability is structural: `RunService` already owns every approval (`runService.ts:204`), so recording `GateDecision`s for both modes is one code path, whereas a step-internal judge would have to smuggle its verdict out through workflow context. Third, failure degrades safely: a judge that cannot produce a verdict leaves the run suspended and a human takes over (FR-005) — in placement (1) a judge failure inside a step can only fail the step, destroying the run over an infrastructure hiccup. Fourth, human override and race-safety come free from the existing single-flight guard (`runService.ts:211-214`). Cost, stated: the judge logic lives in the daemon, so the mode cannot be exercised by a bare Mastra workflow without a `RunService` — acceptable, since every real surface (HTTP, MCP, UI) already goes through `RunService`.

**B. Default `manual`, argued by asymmetry.** The same canon serves a supervised daytime run and an unattended nightly run. A manual-by-default run that nobody attends sits suspended — visible, resumable, harmless. An auto-by-default run that the operator believed was supervised publishes a PR with no human in the loop — the exact silent-check failure class this project keeps finding in itself. The nightly scheduler is an explicit caller and passes `gateMode: "auto"` explicitly; defaults exist to protect the ambient case. Manual default also makes FR-002's backward compatibility exact: a request without the field behaves byte-identically to today.

**C. Rejection terminates the run — one mechanism instead of a skip matrix.** Today's continue-and-skip semantics are honored by exactly two step kinds (Context §2); making every other kind gate-aware was considered and rejected: it requires wrapping llm, check, assemble, merge, and loop constructs, and it still leaks — loop bodies are built from their own step lists (`build.ts:125-139`), where `findGateAncestor` (`build.ts:59-69`) cannot see a parent-level gate, so a rejected plan gate in `cycle` would still execute `build`'s converge loop. Throwing `GateRejectedError` at the gate stops everything downstream by construction, in every nesting shape, with one ~10-line change. The semantic shift is owned honestly: a rejected `spec-creation` run now ends `failed` with `Gate "approve" rejected …` instead of `success` with a silently-discarded ticket. Nothing was ever persisted on rejection anyway (`buildSteps.ts:380`), so the substance — "rejection produces no artifact" — is preserved; what changes is that the run's terminal status now tells the truth, and the MCP `approve` description (`bindings/mastra/server.ts:152`) is updated to match. A distinct `"rejected"` terminal status was rejected as surface churn: every consumer (UI, SSE, MCP, tests) would grow a fourth state to render, for information `gateDecisions` + the error string already carry.

**D. Independence and the judge's evidence.** Independence is structural, not aspirational: every `runLlmStep` invocation is a fresh one-shot CLI process with `--restricted` isolation (Context §8) — the judge shares no session, no context window, and no conversation history with the steps that produced the work. What it is given is deliberately the human's-eye view plus the human's hands: the same `gateMessage` + `spec` payload the manual surfaces show (parity is the contract — the agent answers _in the human's place_), plus read-only access to the working tree and a daemon-captured `git status` — because for `ship`'s gate the spec payload is undefined (Context §1) and the working tree _is_ the material a human would inspect. What it is _not_ given, deliberately: the producing steps' outputs, prompts, or transcripts. Those are the producer's self-report; a judge that grades the narrative instead of the artifact is grading homework by the student's own summary. The judge model is the `reasoner` role — evaluation is the role's purpose, and on the default profile that is the pinned `fable` (`registry.ts:32,68`); the per-run `models` override map does not apply (it keys step ids, and the judge is not a step).

**E. The rubber-stamp problem, treated as first-class.** An auto-gate that cannot reject is this project's canonical defect — a green light that cannot turn red — and it would be invisible precisely because runs would keep succeeding. Five mechanisms make rejection real: (1) the rubric's burden of proof points toward reject — approve requires affirmative verification, and "cannot verify" is defined as reject (FR-010); (2) every failure path — malformed verdict, transport error, watchdog exhaustion, truncated-and-unverified material — lands on _not approved_ (suspended-for-human or reject), never on approve (FR-005); (3) a mandatory evidence-citing reason makes a content-free approval structurally malformed; (4) every decision is recorded with mode, model, and reason (FR-008), so a drift toward 100% approval is auditable from run history rather than invisible; (5) the gating live probe T-10 proves, against a real model before ship, that a planted violation is rejected — the test that can fail. And rejection now _does something_: FR-006 guarantees a reject verdict stops the PR, in both bindings.

**F. Per-step manual pin (`manualOnly`) — decision made per owner directive 2026-09-07.** A canon field pinning a gate to manual regardless of run mode was considered and originally recommended against because: the owner's decision was run-level, and a pinned step makes `"auto"` mean "mostly auto" — an unattended nightly `cycle` would hang at a pinned gate, the worst of both modes (nobody watching, nothing progressing). The architect argued the blast radius of a wrong auto-approval at `ship` is bounded: a PR is visible, reviewable, and closeable — not a merge — and FR-008 records who approved it and why. However, the owner overruled this, deciding that commit and PR creation's irreversibility justifies an always-manual gate at `ship`, and the pin is now required (FR-013, FR-014). Consequence, stated plainly: an unattended auto run will halt at a pinned gate (`ship.approve`) and wait indefinitely for a human. This is an accepted, intended property. A future auto mode without such a pin at `ship` would be a policy decision for later; the spec does not prohibit it.

**G. n8n binding — what is fixed and what is honestly unverified.** The spec fixes the node _types_ and the _topology_: mode-IF → (Wait + approved-IF | HTTP Request + verdict-IF), with reject branches unconnected so irreversible nodes are unreachable without an approval — n8n's own branching solves the Context §2 hole in that binding. Unverified, because this repo contains no n8n runtime and no node parameter schemas: the exact Wait-node parameters for webhook resume, whether the resume payload is exposed to the downstream IF in the assumed shape, and the current IF-node condition schema version. Implementation must resolve these against n8n documentation and prove them with the round-trip import test, not assume them. The auto branch calls the daemon (FR-012) rather than embedding an LLM node so both bindings share one judge implementation and one rubric — two judges would drift.

## Backward compatibility

- Requests without `gateMode` behave as today at every surface: manual is the default, and manual approval flow, suspension payloads, and the MCP tool schemas are unchanged (the `approve` tool gains no fields; its description text is corrected per Design C).
- Canon gains one additive optional field: `manualOnly: boolean` on gate steps (FR-013, FR-014). Pipelines that omit it behave exactly as before; existing pipelines load unchanged.
- Requests without `manualOnly` on a gate are treated as `manualOnly: false` and behave exactly as today.
- **Intentional break 1 (FR-006):** rejecting a gate now fails the run with `GateRejectedError: Gate "<id>" rejected …` instead of continuing with skipped persist/export. Today's continue-after-reject behavior is the defect that commits and opens a PR after a rejection (Context §2); preserving it is not an option.
- **Intentional break 2 (FR-007):** approve responses for processed-but-failed resumes change 409 → 200-with-failed-state. Callers keying on 409 for "not suspended" are unaffected — that case still 409s.
- `GetResult` gains only additive fields (`gateMode`, `gateDecisions`, `judgeError`); SSE and MCP consumers that ignore unknown fields are unaffected.
- n8n exports change shape for pipelines containing gates (NoOp → branch subgraph); previously exported JSON in n8n instances is not migrated — re-export is the mechanism, consistent with the binding being a one-way emit today.

## Out of scope

- A distinct `"rejected"` terminal run status (Design C) and any persistence of `gateDecisions` beyond the in-process `RunRecord` (spec 020's restart posture governs).
- Per-gate or per-pipeline judge model selection, judge budget caps, and multi-judge quorums.
- A feedback loop from a rejection back into the pipeline (e.g. re-running `correct-plan` with the judge's reason) — the reason is recorded for exactly this future use, but the loop is its own spec.
- Human "reason" capture on manual approvals from the UI/MCP surfaces (the field exists in resume data; wiring input affordances is deferred).
- Implementing spec 020; this spec only keeps its data on the record 020 will read.
- Executing loop/export-spec/assemble NoOps in the n8n binding — only `gate` graduates here.

## Test plan

1. **Mode default and validation** — `POST /api/runs` without `gateMode` yields a run whose `GetResult.gateMode` is `"manual"`; `gateMode: "auto"` is stored; `gateMode: "yolo"` is a 400 naming the field; same three cases through the MCP `run_pipeline` tool.
2. **Manual mode regression** — a gated run without `gateMode` suspends, surfaces `gateMessage`/`spec` via GET and SSE snapshot as today, resumes on approve; `gateDecisions` records `{ decidedBy: "human", approved: true }`.
3. **Auto approve end-to-end** — stubbed judge runner returns a valid approve verdict: the run never settles as `awaiting_approval`, proceeds past the gate, completes, and `gateDecisions` carries `{ mode: "auto", decidedBy: "agent", approved: true, reason, judgeModelId }`.
4. **Auto reject stops the irreversible steps — the case this spec exists for** — `ship` fixture with spied check execution: stubbed judge returns reject; the run ends `failed` with `GateRejectedError` naming the gate, mode, and reason; the `commit` and `pr` check commands were **never executed**. Companion pin on today's defect: the same fixture on current `main` semantics executes `commit` after `approved: false`, proving the inversion.
5. **Manual reject terminates too** — `approve(runId, false)` on a manual run: run `failed`, downstream steps never ran, HTTP approve response is **200** with the failed state (FR-007); approving a non-suspended run still returns the 409.
6. **Malformed judge never approves** — stubbed judge returns prose (no JSON), then an empty-reason object: exactly 2 judge invocations, run **remains suspended**, `judgeError` set and visible in `GetResult`, gate still answerable by a human whose subsequent approval works. Repeat with the judge throwing (transport error): same outcome. Assert no path set `approved: true`.
