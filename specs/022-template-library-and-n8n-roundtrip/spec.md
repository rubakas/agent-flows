## Context

The division of surfaces is settled and is a requirement of this spec, not a question it re-opens: **the agent-flows web UI is a project inventory and library manager** — it answers, fast, what is in this project directory, which workflows are here, and whether any need adding; from it the operator can view a workflow, delete it, and create one from shipped or saved templates. **n8n is the authoring surface**: a brand-new workflow is created in n8n, and editing an existing one happens in n8n via a redirect button in our UI. The bridge back is that a workflow authored in n8n can be saved into agent-flows as a template in a **global** (not project-scoped) directory, for later insertion into any project.

Consequence for spec 020: the run-watching half of that spec — the UI run list/picker, mid-run attach rendering, its DOM-escaping FR, and the layout FR (020 FR-003, FR-004, FR-007, FR-009) — is **not this UI's job and is deferred there**. Only 020's API half remains relevant: run listing, per-step output, and the unified MCP/HTTP registry (020 FR-001, FR-002, FR-005, FR-006, FR-008), because those serve chat.

Verified gaps against that shape:

1. **There is no global user-level template store.** The project-scoped install target is `<projectDir>/.agent-flows/` with `pipelines/` and `prompts/` (`src/install/install.ts:82,105-119`), `listInstalled()` reads `<projectDir>/.agent-flows/pipelines/` (`install.ts:132-140`), and the runtime resolves project → bundled only (`src/bindings/mastra/pipelineLoader.ts:57-68`, bundled dir at `:11`). Nothing resolves a `~/.agent-flows` or equivalent; the only home-level lookup is skills: `AGENT_FLOWS_SKILLS_DIR` defaulting to `~/.claude` (`src/serve/server.ts:305-306`), and that is for skills, not pipelines.

2. **There is no n8n → canon importer.** `src/bindings/n8n/` contains only `build.ts` (canon → n8n: one node per step, connections from `dependsOn`, `build.ts:136-201`) and `write-cli.ts` (batch JSON writer). The forward direction is itself lossy today: only `llm` and `check` steps map to real node types (`build.ts:72-89`); `gate`, `loop`, `export-spec`, `assemble-spec`, and `persist-ticket` all collapse to `noOp` with explanatory notes (`build.ts:91-120`).

3. **The UI has no n8n awareness at all**: zero occurrences of "n8n" in `src/serve/ui.html` (verified by grep, 2026-09-07).

4. **Transport already exists and must be reused.** Bundle export/import (`src/install/bundle.ts`) serialises a pipeline's transitive closure to one portable YAML (`bundle.ts:34-76`), validates with a temp-dir + `loadPipeline` phase before writing anything (`bundle.ts:166-220`), and is already wired to `POST /api/import` (`server.ts:909`) and the export route (`server.ts:887`). This spec adds no second transport.

n8n facts this spec relies on (citations inline): the public REST API lives under `/api/v1`, authenticates with an API key created at **Settings → n8n API** and sent in the `X-N8N-API-KEY` header ([docs.n8n.io/connect/n8n-api/authentication.md](https://docs.n8n.io/connect/n8n-api/authentication.md), including the `GET …/api/v1/workflows?active=true` curl example). Retrieval is `GET /api/v1/workflows/{workflowId}` and creation is `POST /api/v1/workflows` with required body fields `name`, `nodes`, `connections`, `settings`; `id` and `active` are readOnly on the request and the server-assigned `id` comes back in the response (n8n repo, `packages/cli/src/public-api/v1/handlers/workflows/spec/paths/getWorkflow.generated.yml` and `createWorkflow.generated.yml`; schema in `…/spec/schemas/workflow.yml`, whose `connections` example — `{ Jira: { main: [[{ node: 'Jira', type: 'main', index: 0 }]] } }` — matches what `build.ts:164-191` emits). The editor routes are `path: '/workflow/new'` and `path: '/workflow/:workflowId/:nodeId?'` (n8n repo, `packages/frontend/editor-ui/src/app/router.ts`); the workflow ID is visible in "the URL of the open workflow" ([docs.n8n.io/build/understand-workflows/workflow-components/find-your-workflow-id.md](https://docs.n8n.io/build/understand-workflows/workflow-components/find-your-workflow-id.md)).

A parallel spec, `specs/021-n8n-interpolation/spec.md`, exists and covers the forward expression mapping. **FR-008's assumed inverse mapping MUST be reconciled against it** (verified 2026-09-07), as the two must be exact inverses.

## Design

**Templates are bundle files, one per template (FR-001/FR-002).** The alternative — an expanded `~/.agent-flows/templates/<id>/{pipelines,prompts}` tree — was rejected: it needs recursive listing, invites partially-written template state, and requires a second import path, when `bundle.ts` already gives atomic single-file templates, validation-first import, and human-diffable YAML for free (`bundle.ts:1-6`). Listing a template = parsing one file's header fields; deleting = deleting one file.

**Tiers are install-time sources, not a runtime overlay (FR-003).** The alternative — teaching `resolveCanonDir` a three-way project → global → bundled fallback — was rejected: it makes "which file actually runs" ambiguous across every surface (serve, MCP, editor) and touches the loader every binding depends on. Committing to "runtime resolution stays project → bundled (`pipelineLoader.ts:57-68`); global templates only ever _install into_ a project" keeps the change surface to new routes plus the store, and makes tier labels in the UI truthful: only the project tier executes.

**Importer strictness (FR-007) is the load-bearing decision.** Best-effort import (unknown node → `noOp`-like placeholder step) was rejected on the owner's explicit requirement: arbitrary n8n nodes are the normal case, and a silently lossy import produces a canon file that lies about what the operator built. Failing with the node's name and type costs one retry after the operator swaps the node for a supported one; a silent loss costs a corrupted template discovered much later inside a different project. The forward direction's own TODOs (`build.ts:74,92,97,108,119`) mark where future typed nodes will widen the supported set; each widening is a new mapping row here, not a relaxation of the failure rule. Even visual-only nodes are rejected in v1 — an explicit ignore-list can be added later as a one-line, stated exception.

**Credentials (FR-004/FR-005).** An API key pasted once into a home-directory config file is the entire authorisation story; the operator's n8n password never passes through agent-flows in any direction. The key stays daemon-side because the daemon proxies every n8n call — the browser only ever learns `baseUrl` and workflow `{id, name}` pairs. This also means the redirect buttons work even though the _editor_ session in the browser authenticates however the operator's n8n does; agent-flows only builds URLs (`/workflow/new`, `/workflow/<id>` — router.ts citation in Context) and never participates in that session.

**Workflow-id mapping (FR-006).** The pipelineId → n8n-workflow-id map must be stored, because n8n assigns the id at creation (request `id` is readOnly — createWorkflow spec, Context) and nothing in the repo records it today (`write-cli.ts` writes JSON files and discards nothing because it never talks to a server, `write-cli.ts:15-24`). A per-project JSON file beside the pipelines (`.agent-flows/n8n.json`) was chosen over a table in `agent-flows.sqlite`: the mapping is project-scoped exactly like the pipelines it describes, travels/deletes with `.agent-flows/`, and is operator-inspectable with no schema migration. Stale mappings self-heal via the 404-recreate rule.

**Failure paths.** n8n unreachable or key rejected: daemon returns the n8n status code and a message naming the config file — never the key. Import failure: FR-010 guarantees zero writes; the error names the offending node/parameter. Template install collision: skip-and-report by default, `overwrite` opt-in — identical semantics to `installWorkflow` (`install.ts:95-103`).

## Backward compatibility

- No existing route changes shape. `POST /api/import` (`server.ts:909`) and the export route (`server.ts:887`) keep working; a template file is a valid bundle for them by construction.
- The bundle format is unchanged (`bundleVersion: 1`); templates introduce no version bump.
- `resolveCanonDir`, `installWorkflow`, and `listInstalled` are untouched; existing projects see no behaviour change until the operator uses a template or the n8n buttons.
- `generateN8nWorkflow` output is unchanged; the importer is additive. The known forward losses (FR-012) are the same losses that exist today — this spec documents them rather than widening them.
- New behaviour on failure: workflows containing unsupported nodes now produce a hard import error instead of there being no import at all — nothing regresses.

## Out of scope

- Removing or rebuilding the existing draft-editor and run panels in `ui.html` — this spec adds the library surface and n8n buttons; demolition of the in-house editor is a separate cleanup once the n8n path is proven.
- The run-watching UI (the deferred half of spec 020, per Context).
- Executing `gate`, `loop`, nested `pipeline`, `export-spec`, `assemble-spec`, or `persist-ticket` in n8n, and therefore round-tripping them (blocked on the `build.ts` TODOs; FR-012 states the bounded consequence).
- Supporting arbitrary n8n node types or expression syntaxes beyond FR-007/FR-008's sets.
- Two-way live sync with n8n (watching for edits, auto-pull); the save-back is an explicit operator action.
- Multi-operator concerns: auth on the new routes (daemon stays loopback-only, `server.ts:335`), template sharing, per-user stores.
- n8n Cloud trial limitations (the public API is unavailable on the free trial — connect/n8n-api doc); the operator is assumed to run an instance with API access.

## Test plan

1. **Loud failure on unsupported node, zero writes** — an n8n workflow fixture containing an `n8n-nodes-base.httpRequest` node named "Fetch stuff": `POST /api/templates/from-n8n` (n8n mocked) returns an error whose message contains both `Fetch stuff` and `n8n-nodes-base.httpRequest`; asserted explicitly — the templates directory is byte-identical before and after (no file created, no partial writes).
2. **Round-trip lossless for llm/check** — take a bundled pipeline with only `llm`/`check` steps, run `generateN8nWorkflow` → importer: step ids, kinds, `dependsOn`, `role`, `model`, `skills`, `permissions.contents`, and every prompt file's text are equal; the FR-012 declared-loss fields are at their documented defaults.
3. **Round-trip refusal for gate** — export a pipeline containing a `gate` step (becomes `noOp`, `build.ts:91-93`), re-import: loud error naming the node and stating the kind cannot be re-imported; nothing written.
4. **Expression inversion** — a fixture prompt containing `{{ $json.ticket }}` and `{{ $json.analyze }}` where `analyze` is a node name: imported prompt file contains `{{ticket}}` and `{{analyze}}`, pipeline `inputs` contains `ticket` and not `analyze`. A fixture containing `$('Other').item.json.x` fails loudly naming node and parameter.
5. **Validation backstop** — a fixture whose inverted prompt references a name that is neither an input nor an ancestor step: import fails via `loadPipeline`'s placeholder check (`load.ts:372-378`) and writes nothing.
6. **Template lifecycle** — save a mocked n8n workflow as a template: exactly one `<templateId>.yaml` appears in the templates dir and parses via `parseBundle`; `GET /api/templates` lists it; `POST /api/templates/:id/install` writes into `<projectDir>/.agent-flows/` with skip-on-existing semantics; `DELETE` removes the file; a second save without `overwrite` returns 409.
7. **Path containment** — `DELETE /api/templates/..%2F..%2Fescape` and a templateId of `../escape` are rejected before any I/O.
8. **Key secrecy** — with a configured `n8n.json`, capture every daemon response and log line across status, list, redirect, and save-back (including forced error paths with the mock returning 401): the API key string appears in none of them; `GET /api/n8n/status` returns only `{configured, baseUrl}`.
9. **Redirect mapping** — "Edit in n8n" on a project pipeline (mock assigns id `w123`): response URL is `<baseUrl>/workflow/w123`, and `.agent-flows/n8n.json` maps the pipeline id to `w123`; a second press issues no create call; after the mock 404s the stored id, a new create is issued and the map updated. Unconfigured n8n returns the actionable error naming `~/.agent-flows/n8n.json`.
10. **UI escaping (manual or DOM test)** — a template whose source workflow name is `<img src=x onerror=alert(1)>` renders as escaped text in the inventory and the picker.
