## Context

The owner's requirement, verbatim: _"я хочу workflows для task formulation, development, security, tests, audit and self-improvement, composed into one process that accepts either a feature request or an already-written task description, so I can run it and review the result rather than supervise each prompt. It must be convenient, cheap and safe. And — this is the requirement that shapes everything — it must survive its provider: if Claude is down, the same process must continue on GPT or on a local model."_

A working solution exists: the canonical pipeline system, organized as short stages with human judgment gates between them (`spec-creation`, `develop`, `build`, `test`, `audit`, and future `security` and `self-improvement` stages) that can be composed and re-run. The owner has explicitly rejected the "mega-pipeline that runs unattended end to end" model — the most expensive failure in agent work is a wrong premise carried far, and a long unsupervised chain maximises it. Instead, stages hand off to the next manually: the operator reviews each result and decides whether to proceed.

The present gap: that handoff has no concrete mechanism. A stage's output lives in the run's accumulated context, stored only in daemon memory (a `Map<string, RunRecord>` at `src/runtime/runService.ts:223`). Runs do not survive a daemon restart — by design (spec 026 FR-007/Design C); so there is no durable artifact for a later stage — or a different provider — to pick up. This is why "continue the same process on GPT when Claude is down" is impossible today. It is also why a human reviewing stage N cannot easily hand the result to stage N+1 on a different machine or after a reboot.

**Findings, verified 2026-09-08:**

1. **No durable artifacts exist today.** Run outputs live in daemon memory (runService line 223: `private readonly registry = new Map<string, RunRecord>()`). GetResult exposes `result`, `spec`, and gateDecisions; all three are in-process objects, never written to disk.

2. **Stages accept different inputs.** Read from YAML: `cycle` and `cycle-dev` accept only `request`; `build`, `develop`, `audit`, `ship` accept `plan`; `correct-plan` accepts both `plan` and `findings`; `investigate` accepts `request`. There is no entry point that accepts an already-written task and skips formulation.

3. **Provider portability is designed but unproven.** Three profiles exist in `src/canon/registry.ts` (lines 94–110): `anthropic` (opus/sonnet/haiku), `openai` (codex), `local` (ollama-qwen). Transports (`cli` and `api`) are implemented and covered by unit tests at `src/canon/runStep.test.ts` (lines 30, 80, 142: claude CLI, codex CLI, API). **Not verified from code**: no pipeline has ever been run end to end on the `openai` or `local` profile; this spec's verification gate requires that proof (V-9).

4. **Security and self-improvement are missing as stages.** The audit pipeline includes a `security` step (audit.yaml:13–18), and spec-creation includes a `security` step (spec-creation.yaml:25–30), but both are review steps inside other pipelines, not stages. No self-improvement stage exists.

5. **No operator guidance on entry point selection.** The daemon accepts `POST /api/runs` with `pipeline` and `inputs` fields (server.ts:641–676), but nothing tells the operator "if you have a request, enter at spec-creation; if you have a plan, enter at build." The MCP binding's run_pipeline tool accepts the same and has no guidance either (bindings/mastra/server.ts:99–136).

## Design

**A. Artifact layout: location inside the project, with `.gitignore` default-ignore.** Three options were considered. (1) _Write artifacts outside the project, in a cache directory_: rejected — the operator cannot version them, share them with teammates, or use git to audit the record. (2) _Write them inside the project, commit by default_: rejected — artifacts contain model output that may include full repository content (the audit and review steps read most of the codebase as context), and committing that by default would bloat the repository and violate privacy if the repo is public. (3) _Write inside the project, default-ignore, operator-controlled_: committed. The `.agent-flows/.gitignore` file is created on first install or first run with `runs/` as the default line. The operator can override it to preserve selected artifacts for audit trails, maintaining the principle "what's in git is the operator's explicit choice." Artifacts are JSON (readable, diffable if committed) and uncompressed (no extra tooling needed to inspect them).

**B. Per-step provenance recording without per-step token logging.** The `provenance.transportPerStep` map records which transport and model ran each step. For `cli` transport (claude, codex), recording is structural: the registry entry id and the transport. Token counts are **not** captured from CLI transports in this spec because the child process' stderr is noisy and parsing would be brittle; the daemon would see "input tokens: 123" in logs but cannot distinguish it from other lines. The cost of this gap (not knowing claude's actual token usage per step) is acceptable because (a) the provider is visible (the operator can see "this audit ran on claude"), and (b) a future spec can add structured logging from the CLI when prompt-injection hardening is in place. For `api` transport (ollama, litellm), the endpoint response includes usage; it is captured and recorded. This asymmetry is stated in the design docs and test stubs should assume it.

**C. Entry-point routing as an explicit rule, not a model guess.** The `POST /api/runs/decide` endpoint runs a simple function: check if the input is a file path, load it, check for artifact signature fields, and recommend a pipeline. This is deterministic and inspectable — the operator can see the decision before submitting. It never calls a model. An operator can override the recommendation by specifying `pipeline` directly in the subsequent `POST /api/runs` call. This is the opposite of "have a model decide where to start" — it is a safeguard against wrong premises carried far, which is precisely why the owner rejected the mega-pipeline model.

**D. Why not merge "stages" into runs, and why separate runs per stage?** Architectural decision: each stage is a separate `MastraRun` (a separate invocation of `runService.start()` with its own runId, record in the registry, and lifecycle). This is correct because: (1) each stage may run on a different provider and at a different time, so a unified run object would have to carry provider context through the chain (added complexity). (2) The operator may interleave or skip stages (e.g., review the audit output and decide to go back to develop, or jump to build without running develop first), so a linear run DAG is too rigid. (3) Stages are independently stoppable (spec 026: a user can cancel a hung audit and decide to proceed anyway) — if they were one run, cancelling the audit would kill the whole chain. (4) Manifests and chains naturally represent runs as a sequence of linked artifacts, and that is exactly what the operator needs to see. The cost is that the operator must call the API multiple times; this is the intended design, not a limitation.

**E. No token-budget enforcement across stages.** Spec 020 defines per-run token budgets. This spec treats each stage as a separate run, so each stage gets its own budget. A chain of three stages can spend 3× the single-run budget; this is acceptable because the operator controls the chain composing and can set budgets per stage. Cross-stage budgeting (e.g., "stop after spending $50 total across all stages") is a future spec.

**F. Artifact validation and boundary-crossing.** When a stage input points to an artifact from a different project or even a different codebase (via an absolute path in `artifactPath`), the daemon reads and uses it without validation. This is a feature: the operator might run spec-creation in one project, export the spec, import it into another project, and run develop there. No validation means no locked-in assumptions. The risk is the operator's to manage — if the artifact is corrupted or the fields are missing, the stage fails (and can be retried or skipped). This follows the principle "trust the operator's intent over guardrails."

## Prior art

Three systems were surveyed:

1. **Claude Code dynamic workflows** (first-party, Anthropic, subscription-only): Offers mid-run user input, pause/resume, per-agent token accounting, and built-in model switching. However, its documentation states plainly "No mid-run user input" in the sense of a human reviewing and approving a major decision point like a plan or a spec, and "For sign-off between stages, run each stage as its own workflow". The tool is bound to Anthropic's infrastructure (no self-hosted, no multi-provider).

2. **Vibestrate** (commercial, closed-source): Orchestrates Claude Code, Codex, and local agents with per-step model seats, approval stops, and a cost log. Designed for teams and enterprises; not open source; no tooling to port a workflow to a different provider if a vendor changes pricing or shuts down.

3. **open-dynamic-workflows** (MIT, GitHub): Script-as-orchestrator across OpenAI Code, Codex, and Gemini CLI with Anthropic/OpenAI/Ollama providers, crash-resume via SQLite, token budgets. 36 stars, 79 commits, young. The closest free equivalent in spirit; worth re-evaluating before this spec's successors are built, especially for crash-resume and multi-provider orchestration patterns.

This spec diverges from all three by treating the artifact, not the orchestrator, as the source of truth — the operator chains stages via explicit function calls, and each artifact is self-contained and readable. This philosophy trades orchestrator logic for transparency: the operator sees and controls the flow.

## Backward compatibility

- Existing `POST /api/runs` route keeps its shape; `artifactPath` is an optional new field.
- Existing `GET /api/runs` and `GET /api/runs/:id` remain; their responses gain optional `artifactPath` and `provenance` fields (additive).
- `GetResult` gains two new fields: `artifactPath` and `provenance`. Consumers that ignore unknown fields are unaffected.
- No existing fields are removed or renamed.
- New routes (`POST /api/runs/decide`, `GET /api/runs/:id/manifest`) do not conflict with existing routes.
- MCP: `run_pipeline` gains optional `artifact_path` parameter (existing calls omit it and work unchanged). New `decide_entry_point` tool does not affect existing tools.
- `.agent-flows/.gitignore` is created or updated to add `runs/` if it is not already present; if the operator has already customized this file, the line is not re-added (do not overwrite explicit operator intent).

## Out of scope

- **Run cancellation and persistence across daemon restarts** (spec 026): cancelling a stage, resuming mid-stage, or rehydrating a killed run are separate concerns. This spec assumes stages are atomic: once started, a stage runs to completion or to a gate suspension, then the operator decides what to do next.
- **Security and self-improvement stages** (future spec): the audit pipeline includes a security step, but there is no separate security stage. Self-improvement does not exist. Both are wanted and absent; a later spec will define them as first-class stages.
- **Making stage output executable** (future spec): this spec writes JSON artifacts. Running an artifact as a new stage (e.g., "execute this spec as code") is the next move and deserves its own spec.
- **Token counts from CLI transports** (Design B): capturing fine-grained token usage from claude and codex CLI is deferred; the transport is recorded, and the operator can infer cost from the model id and the token counts from API transports.
- **Cross-stage token budgets** (Design E): enforcing a total spend across a chain of stages is a future refinement.
- **Artifact signing or provenance chains** (beyond the content): this spec records which provider ran each step; cryptographic signing is not included.
- **Multi-tenant or multi-user artifact isolation** (spec 026 territory): this spec assumes a single-user, single-project daemon. Project-level and user-level isolation are part of a deployment model spec.
- **Webhook or push integration for automated chaining** (Design D): chaining remains explicit and operator-controlled. Automation (script or external orchestrator calling the API) is the operator's choice, not baked in.

## Verification

Every item below can genuinely pass AND fail. The decisive one is V-9, which proves provider portability end-to-end:

1. **Artifact file is written on stage completion.** Run a simple pipeline (e.g., `investigate`). Wait for status `"awaiting_approval"` (gate) or `"succeeded"`. Assert that a file exists at `<projectDir>/.agent-flows/runs/<runId>/investigate.json` and contains valid JSON with all fields from `GetResult` plus `provenance`.

2. **Artifact survives daemon restart.** Write an artifact (V-1). Stop the daemon (e.g., SIGTERM). Start it again. Assert the artifact file still exists and is readable. Assert that `GET /api/runs/<oldRunId>` returns 404 (the in-process registry is empty post-restart, as designed in spec 026), but the artifact file can still be read manually.

3. **Artifact can be read as input to a new stage.** Write an artifact from `spec-creation` (status `"awaiting_approval"`). Start a new run with `POST /api/runs { "pipeline": "build", "artifactPath": "/abs/path/to/artifact" }`. Assert the new run starts and its `steps[0].inputData` contains the `spec` from the artifact. Run should succeed or fail based on the content; the artifact was successfully consumed.

4. **Entry point decision rule: artifact signature routing.** Call `POST /api/runs/decide { "input": "/path/to/artifact.json" }` where the artifact has `spec` and `gateDecisions` fields. Assert the response is `{ pipeline: "develop", reason: "..." }` or a similar development-tier pipeline. Call with an artifact that has `findings` field only. Assert the response routes to `spec-creation` or investigate-feedback chain. Call with a plain text string (not a file). Assert the response is `{ pipeline: "investigate", reason: "..." }`.

5. **Different providers per stage.** (a) Run a stage with `AGENT_FLOWS_PROVIDER=anthropic`. Write the artifact. (b) Start a new stage with `AGENT_FLOWS_PROVIDER=openai` and `artifactPath` pointing to the anthropic artifact. Assert the new run starts. Check the second artifact's `provenance.profileId` is `"openai"`. Assert the stage produces valid output (may differ in quality, but the handoff succeeded). This is the core test that "continue on GPT when Claude is down" is not aspirational.

6. **Provenance records transport and model per step.** Run a multi-step pipeline (e.g., `spec-creation` which has `intake`, `enrich`, `critic`, `security`, etc.). Wait for completion. Read the artifact. Assert `provenance.transportPerStep` has entries for each step, e.g. `{ intake: { transport: "cli", model: "claude-sonnet-5", modelId: "sonnet" }, ... }`. For at least one step, verify that the model name in the artifact matches the registry entry.

7. **Artifact JSON is readable without the daemon.** Write an artifact. Stop the daemon. Read the file with `cat` or a JSON parser (e.g., `jq`). Assert the file is valid JSON and contains the expected fields (`runId`, `pipelineId`, `status`, `result` or `spec`, `provenance`). No binary format, no compression, no daemon required.

8. **Manifest tracks the chain of stages.** Run `investigate`, then `spec-creation`, then `build` (each a separate `POST /api/runs` call with `artifactPath` pointing to the previous stage's artifact). After all three complete, read `<projectDir>/.agent-flows/runs/<runId>/manifest.json`. Assert it lists all three stages in order with their artifact paths, provider ids, and completion status. Assert that the manifest is updated after each stage completes.

9. **Provider portability end-to-end (decisive).** This is the test that validates the entire goal. The proof requires separate runs handing off via durable artifacts — not one run paused under one provider and resumed under another. (a) Run `spec-creation` (or a simpler single-stage pipeline like `investigate`) with `AGENT_FLOWS_PROVIDER=anthropic` on a test project. Let it run to completion (terminal status `"succeeded"`). Read the artifact at `<projectDir>/.agent-flows/runs/<runId1>/spec-creation.json` (or `investigate.json`). Assert it contains the `spec` (or `result`) field and `provenance.profileId` is `"anthropic"`. (b) Stop the daemon completely (SIGTERM or equivalent). (c) Set `AGENT_FLOWS_PROVIDER=openai` (or `local`). Start the daemon again. (d) Call `POST /api/runs { "pipeline": "build", "artifactPath": "/abs/path/to/anthropic-artifact", "gateMode": "manual" }`. This starts a NEW run (`runId2`) under the openai provider. (e) The build stage starts and reads the `spec` field from the anthropic artifact as its input. (f) Let build run to completion. (g) Read the build artifact at `<projectDir>/.agent-flows/runs/<runId2>/build.json`. Assert `provenance.profileId` is `"openai"`, the `spec` field matches what was read from the anthropic artifact, and the output is coherent (may differ in quality from anthropic's, but the stage ran and produced results). (h) Assert that the procedure described above succeeds; it should fail today because no durable artifact exists. This test proves the spec's central claim: stages hand off via persisted artifacts, enabling a run to continue on a different provider after a clean restart.

10. **Gitignore default: runs/ is ignored by default.** Run a pipeline and generate an artifact. Call `git status` or inspect `.agent-flows/.gitignore`. Assert that `runs/` is listed and the artifact files are not shown by `git status`. If `.agent-flows/.gitignore` did not exist, it is created. If it existed and was customized by the operator, the new line is not re-added (test both cases).

11. **No unattended chaining.** Run `investigate`. Assert that there is no automatic follow-up call to `spec-creation`. The manifest shows only `investigate` complete. The operator must explicitly call `POST /api/runs { "pipeline": "spec-creation", "artifactPath": "..." }` to proceed. No webhook, no auto-trigger, no implicit next stage.

12. **MCP decide_entry_point tool.** From chat, call a new tool (or simulated call) `{ "tool": "decide_entry_point", "input": "I have a feature request to add dark mode" }`. Assert the tool returns `{ pipeline: "investigate", reason: "..." }`. Call with `{ "input": "/path/to/artifact.json" }` where the artifact has `spec` field. Assert it returns a develop-tier pipeline. The tool is now the entry point recommendation in chat.
